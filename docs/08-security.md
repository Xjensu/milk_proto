# Security Specification

Addresses the ТЗ's explicit "Тестирование на безопасность" stage: this document is what
that stage's penetration test should be checked against. Covers policy decisions not
already fully specified in `02-slice-authentication.md`.

## 1. Password policy

- Minimum 10 characters, must contain at least 3 of {lowercase, uppercase, digit,
  symbol}. Checked in the `PATCH /auth/me/password` and `POST /admin/users` /
  `POST /admin/users/:id/reset_password` contracts (`05-backend-patterns.md §3`).
- Reject passwords found in a bundled common-password list (top 10k) — a simple
  `dry-validation` rule against a static Set, no external API call.
- Temporary passwords generated by admin-provisioning are 16 random characters
  (base58, no ambiguous glyphs), shown to the admin exactly once in the API response and
  never logged or emailed in plaintext.
- `bcrypt` cost 12 (§`02-slice-authentication.md §4`); re-hash on login if a future cost
  bump is deployed (standard bcrypt upgrade-on-login pattern).

## 2. Token security

- Access tokens: RS256, 15 min TTL, in-memory only on the client
  (`06-frontend-architecture.md §5`) — never `localStorage`/`sessionStorage`, closing the
  most common XSS-token-theft vector.
- Refresh tokens: opaque, `httpOnly` + `Secure` + `SameSite=Strict` cookie, rotated on
  every use, reuse-detection revokes the full token family
  (`02-slice-authentication.md §1`).
- The 15-minute window where a disabled account's still-valid access token could
  theoretically be used is closed to ≤60s by the Redis-cached active-status check on every
  request (`02-slice-authentication.md §5`) — document this trade-off explicitly to
  reviewers rather than claiming instant revocation.
- Role **downgrades** (revoking a `role_assignment` without disabling the account) are
  made effective within seconds — not the token's remaining TTL — via the `rv`
  roles-version claim checked against a Redis counter on every request
  (`02-slice-authentication.md §5`). Without this, a demoted admin's JWT would keep its
  old role snapshot for up to 15 minutes.
- `must_change_password` is enforced **server-side** in the `Authenticate` step (all
  routes except password-change/`me`/logout return `403 password_change_required` while
  the flag is set) — the frontend redirect is UX only and bypassing it via direct API
  calls gains nothing.
- JWT signing key (`JWT_PRIVATE_KEY`) is an env-injected secret, rotated via a documented
  manual procedure in `../deployment.md`; rotating it invalidates all outstanding access
  tokens (acceptable — they're short-lived) without touching refresh tokens (which are
  DB-backed, not signature-dependent).

## 3. RBAC enforcement

- **Every** admin/me action enforces `Authenticate` + `Authorize` server-side
  (`02-slice-authentication.md §5`); the frontend's `RoleGuard`
  (`06-frontend-architecture.md §2`) is UX-only and must never be treated as a security
  boundary in review — this is called out explicitly so a reviewer doesn't mistake
  frontend route-hiding for actual enforcement.
- Scope checks (`faculty_admin`/`kafedra_admin`) are enforced at the Operation/Repository
  layer, not just the Action layer — e.g. `PATCH /admin/workload/cells/:id` must verify
  the cell's kafedra against the caller's scope even though the route itself has no
  faculty/kafedra in its path, to prevent an ID-guessing scope-escalation (IDOR).
- All `DELETE /me/room_reservations/:id`-style "my own resource" endpoints return `404`
  (not `403`) for another user's resource, per `04-slice-main.md §5`, to avoid confirming
  the existence of other users' data.

## 4. Authentication hardening

- Login (`POST /auth/sessions`) returns an identical `401` body/timing profile for
  "unknown email" and "wrong password" — no user enumeration. The timing half is
  achieved mechanically, not aspirationally: on unknown email the action runs one bcrypt
  comparison against a static dummy digest (`02-slice-authentication.md §3`), so both
  failure paths cost one bcrypt verification.
- Constant-time password comparison via bcrypt's own comparison (inherent to the
  algorithm).
- No password-reset-by-email self-service exists (matches "no self-registration"; resets
  are always admin-initiated, `03-slice-admin.md §1`) — this removes an entire class of
  reset-token-leak vulnerabilities by design.

## 5. Rate limiting

Redis-backed sliding window, enforced at the API layer (not just the reverse proxy, so it
survives being placed behind different infra later):

| Endpoint class | Limit |
|---|---|
| `POST /auth/sessions` | 5 / 15 min per `(ip, email)` pair, plus 20 / 15 min per IP regardless of email (credential-stuffing guard) |
| `POST /auth/sessions/refresh` | 30 / 15 min per user |
| All other authenticated writes | 300 / min per user (generous — protects against runaway client bugs, not a primary security control) |
| `/public/*` reads | 120 / min per IP |

Exceeding a limit returns `429` with the `rate_limited` error code
(`05-backend-patterns.md §6`).

## 6. Input validation & injection prevention

- Every write action validated by a `dry-validation` Contract before touching the DB
  (`05-backend-patterns.md §3`) — no action trusts raw params.
- All DB access through Sequel/ROM parameterized queries; the only place raw SQL fragments
  appear is the materialized view definitions and the day-expansion query object
  (`01-database-schema.md §4`), which take no user-supplied string interpolation — all
  inputs are bound parameters.
- User file uploads exist on two paths, both magic-byte validated (not the client-declared
  `Content-Type`) with a size cap and a malware scan before the file is trusted:
  `POST /admin/uploads/media` (images/PDF/DOCX — ClamAV, entropy scan, format-specific
  re-encode that strips metadata and defeats polyglot files) and
  `POST /admin/uploads/excel` (xlsx/xls/GeoJSON — magic-byte + container-structure check,
  ClamAV). See `03-slice-admin.md §11`. Generated PDFs written to MinIO (§9) remain
  server-generated, not user-uploaded.
- CORS: API only accepts the deployed frontend origin(s), configured via
  `ALLOWED_ORIGINS` env var (`../deployment.md`); no wildcard origin.
- Standard security headers on every response: `X-Content-Type-Options: nosniff`,
  `X-Frame-Options: DENY`, `Content-Security-Policy` scoped to the API's own needs (an
  API has no inline scripts to allow), `Strict-Transport-Security` once TLS is terminated
  at the edge.

## 7. Audit logging

Every `create`/`update`/`delete` admin action writes an `audit_logs` row
(`01-database-schema.md §2.1`): `action` (e.g. `faculties.create`, `uploads.create`),
`entity_type`/`entity_id`, `before_data`/`after_data` (a JSON snapshot of the record — see
below for exactly when each is populated), actor `user_id`, `ip_address`. Retained
indefinitely for v1; a retention/archival policy can be added later without schema
changes. The write is best-effort and must never fail the underlying request, but a
failure to record the audit event is itself logged to the application logger rather than
silently swallowed (`06-audit-log-gaps.md`, fixed).

- `entity_id`: populated on `create` (the id of the row the action just wrote — the route
  has no `:id` for creates, so this is captured from the operation's result), and on
  `update`/`delete` (from the route's `:id`).
- `after_data`: populated on `create`/`update` — the record as it looks immediately after
  the write.
- `before_data`: populated on `delete` — the record as it looked immediately before
  removal. Not populated on `update` (would require an extra fetch in every write action
  before the write; judged out of scope — see `06-audit-log-gaps.md`).
- `ip_address`: resolved the same way as the general access log — walks
  `X-Forwarded-For`/`X-Real-Ip` from the right, skipping configured trusted-proxy hops.

`GET /admin/audit_logs` (super_admin only, not detailed as its own slice section since it's
a straightforward filtered list over an existing table — filters: `entity_type`,
`user_id`, `date_from`/`date_to`). Response shape: `03-slice-admin.md §11`.

## 8. File storage (MinIO)

- Bucket `milk-schedule-notices`, private (no public read policy); the API generates
  pre-signed, short-TTL (5 min) download URLs on demand for the "batch print notices"
  feature (`GET /admin/kafedras/:id/notices/print` — generates PDFs for lecture-week/
  exam-session notices per teacher on that kafedra, per the ТЗ's explicit batch-print
  requirement) rather than exposing MinIO directly to the browser.
- API holds MinIO credentials via env vars (`../deployment.md`); the frontend never talks
  to MinIO directly.

## 9. Transport & infrastructure

- TLS terminated at the reverse proxy (nginx/Traefik); internal service-to-service traffic
  (API↔Postgres/Redis/MinIO) stays on the Docker Compose private network, not exposed to
  the host beyond what's explicitly published (`../deployment.md`).
- Postgres/Redis/MinIO ports are **not** published to the host in production compose
  config — only the reverse proxy's 80/443 are.
- Secrets (DB password, JWT signing key, MinIO credentials) via env vars sourced from a
  `.env` file excluded from version control (`../deployment.md` documents the required
  variables, not their values).

## 10. OWASP Top 10 (2021) mapping

| Risk | Mitigation |
|---|---|
| A01 Broken Access Control | Server-side RBAC + scope checks on every action (§3), `404`-not-`403` on foreign-owned resources |
| A02 Cryptographic Failures | bcrypt for passwords, RS256 JWTs, TLS everywhere, secrets never logged |
| A03 Injection | Parameterized queries only, `dry-validation` contracts, no raw SQL interpolation from user input |
| A04 Insecure Design | No self-registration eliminates a whole class of abuse; admin-provisioned accounts only |
| A05 Security Misconfiguration | No wildcard CORS, DB/Redis/MinIO not host-exposed, security headers on every response |
| A06 Vulnerable Components | Dependency updates tracked via `bundle audit` / `npm audit` in CI (`../deployment.md` CI notes) |
| A07 Identification & Auth Failures | Rate limiting, rotation + reuse-detection on refresh tokens, no user enumeration |
| A08 Software & Data Integrity Failures | Migrations reviewed in PRs; no dynamic code loading from user input |
| A09 Logging & Monitoring Failures | `audit_logs` for all mutations, structured request logs with correlation ids for `500`s |
| A10 SSRF | No server-side outbound requests driven by user-supplied URLs anywhere in this domain |

## 11. Penetration-test readiness checklist (ТЗ Stage 3)

Before the security-testing stage, verify: rate limits are active in the target
environment (not just documented), `must_change_password` is enforced end-to-end for the
bootstrap superadmin and every admin-created account, `DELETE` endpoints return `409` not
`500` on FK conflicts, and every `/admin/*`/`/me/*` route has an automated test asserting
`401` with no token and `403` for a token with an insufficient/wrong-scope role
(`05-backend-patterns.md §9`).

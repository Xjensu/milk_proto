# Timetable generation service — design draft

Status: implementation in progress. Updated from the user's September 29 answers. The “token composer” is an algorithm that converts teachers' natural-language wishes into a JSON constraint model. The administrator wants faculty-wide or university-wide generation in a private sandbox, visible progress, conflict resolution resembling a code diff, and one final publication action. A small synthetic scenario accompanies this draft. A read-only published-schedule analyzer and durable private generation runs are connected to the live administrator timetable. The local CP-SAT worker solves a read-only snapshot and stores a proposal without changing published events. Teacher wish submission from the authenticated cabinet and super-administrator review are connected; profile unavailability remains a hard constraint, while text-based unavailable/available wishes are soft preferences. A bulk publish operation reruns the analyzer, checks source freshness and run revision, and commits generated placements plus staged recurring and dated-occurrence edits in one transaction. Administrators can edit generated proposal cells and stage recurring-event moves or dated-occurrence room/date/time/subgroup corrections; generated row day, period, room and supported week parity are editable. Recurring edits preserve source event IDs, teachers, rooms and shared batch membership; dated edits use the existing event-transfer domain operation. Compatible shared lecture streams form one solver placement spanning every linked group and publish as one event batch. Recurring split lessons can be reassigned between their configured subgroups when all affected moves preserve each subgroup's credited hours; dated subgroup overrides are stored on the dated transfer and resolved by the shared occurrence query.

## Source and fit

The [shared Jev discussion](https://chatgpt.com/share/6ab69955-d160-83e9-8c7e-9763c145a697) proposes a hybrid design: deterministic rules and a constraint solver own feasibility; a semantic model, if present, makes bounded typed decisions among already-valid alternatives; a final validator remains authoritative. It cautions against asking a model to build the whole timetable greedily or to calculate dates, arithmetic and hard conflicts. It also describes Jev's `Noul`, `Choice` and `Score` decision primitives, while treating any model probabilities as guidance rather than proof.

That separation maps to this project in two distinct paths. Teacher prose is compiled once into a small, versioned preference IR, grounded against the teacher's workload and profile, then reviewed before activation. Schedule generation expands the authorized snapshot into lesson units and uses CP-SAT to place as many required units as possible before optimizing approved soft wishes and compactness. The published-schedule analyzer, proposal analyzer and transactional publication checks remain authoritative. If a local typed-decision model becomes available and demonstrates value, it can rank bounded feasible alternatives behind the optional decision-model interface; it cannot override constraints or write schedule data.

The conversation's architecture is therefore applied without assuming that Jev itself can be deployed locally. The project's official-material review and local-model smoke checks are recorded below: the reviewed Jev path was hosted, no downloadable local Jev runtime was documented, and the tested small Russian model performed poorly on the frozen wish corpus. The deterministic compiler and local CP-SAT worker are the current dependable implementation; model guidance remains an opt-in experiment with a deterministic fallback.

The [synthetic scenario](scheduler-synthetic-scenario-2026-09-29.json) contains two groups, three teachers, three rooms, four workload requirements, one published lesson, ten teacher wishes covering supported and review-only cases, a private proposed timetable, and expected hard/review analyzer findings. It remains independent of the shared live database. An [executable local prototype](../../apps/scheduler/README.md) compiles supported wishes, analyzes proposals, and generates schedules with CP-SAT. Hanami and Rails now connect it through private durable runs.

## Implemented vertical slice (September 29)

Hanami builds a normalized semester/faculty or university snapshot from current workload, teacher assignments and profile availability, room assignments/reservations, subgroups, published events across the semester as fixed teacher/group/room blockers, dated transfers and weekday transfers. Faculty scope limits generated workload, but fixed resource occupancy remains semester-wide so shared teachers and rooms cannot be double-booked across faculties; unsupported external week parity is conservatively blocked in both weeks. A private queued run is persisted before snapshot construction so the administrator sees progress immediately; unsupported source shapes become explicit terminal preparation failures. The source snapshot is stored with a digest and never returned by the status endpoint. The solver runs on a dedicated internal Docker network with no database credentials or host port. A DB-backed worker claims queued runs using a lease, reports preparation and solve phases, records progress and retries transient failures. A monotonic event sequence is available for polling clients.

Snapshot reads hold the schedule placement transaction lock and then the teacher-preference context lock for the entire multi-query build. Database statement triggers on all 26 source tables use that same lock order, so source changes cannot interleave with a snapshot or the final publication digest check. This is a short critical section around database reads and related writes; solver execution remains outside the transaction.

The Schedule workspace can queue a faculty-wide or university-wide run. Each run is private to its requesting administrator: every read and update, including super-administrator access, must match the requester account; role and schedule scope authorize run creation. The owner can poll its private status and review a labelled placements table with group, subject, teacher, time, room and week parity. While generation is active, the page polls an owner-authorized, run-scoped progress endpoint by event sequence and updates the progress area without reloading the timetable from queue/preparation through solving; it reloads once when the run reaches a terminal state to show the proposal or findings. The analyzer highlights current published conflicts in red, including dated room reservations on dates when affected recurring lessons actually occur. A generated proposal does not write to ordinary schedule tables. Administrators can edit a generated row's weekday, period, assigned room and supported week parity in the sandbox; the API checks run revision/source freshness, restricts parity to the lesson unit's remaining-hour model, and reanalyzes the whole proposal. Existing recurring events can also be moved from analyzer findings into the same private proposal. In-scope published-event conflicts are included in run findings; staging a move removes the original recurring row only from that run's analysis and checks the proposed replacement against availability, room rules and other lessons. Split recurring lessons can be reassigned between configured subgroups; the analyzer requires paired edits to preserve the credited hours of both subgroups, and the publication checklist couples subgroup edits for the same workload. Standalone dated occurrences can be moved to another date/period, have their room corrected or change to another configured subgroup in the same proposal. The subgroup value is stored on the transfer overlay, validated against linked workloads and used by the shared occurrence resolver and final conflict analysis; the published event itself remains unchanged. Shared-event edits are limited to batches fully inside the selected scope; dated edits are shown only when the underlying batch is a single event. Analyzer errors remain visible and block publication. Administrators explicitly check proposal rows for publication; each publish request rechecks selected keys, source digest and revision, runs final analysis, applies staged recurring/dated edits and creates generated placements through existing domain validation and Outbox writes in one transaction. Unselected rows remain private in the same run; after each successful batch the snapshot/digest are rebased to include the published changes, and the run remains proposed until no rows remain. Runtime verification generated proposals, staged recurring parity and placement edits, staged a dated room correction and confirmed that it did not alter the source transfer, and reanalyzed a combined proposal after resolving three profile-availability conflicts. The latter draft reached zero analyzer findings while the live schedule rows remained unchanged; it was intentionally not published. Solver progress is coalesced through the internal API into durable run events; protected heartbeats expose preparation and search while no feasible incumbent exists, then validation. Pinned OR-Tools best-bound callbacks now expose objective-bound updates even before the first feasible solution; incumbent callbacks add feasible-solution count, placed units, branches, conflicts, elapsed time and best objective. Progress writes merge these metrics so a bound callback cannot erase incumbent statistics. Callback access uses a per-run random token stored in the database only as a SHA-256 digest. Recurring-event edits currently support weekday, period, parity changes between even and odd, primary room and paired subgroup reassignment; dated occurrence edits support date, period, primary room and configured subgroup overrides. Dated parity is not a meaningful property of a single occurrence.

Date-specific room reservations, moved-event transfers and weekday transfers are filtered against each scheduled group's configured semester dates before becoming solve blockers. Generation fails explicitly if a workload group has no valid semester date range, rather than applying a one-date exception to an unrelated term or silently ignoring it.

Room capacity is stored as an optional positive integer on each room and can be maintained in the administrator catalog. The solver excludes rooms that cannot seat a whole group; compatible shared lecture streams require capacity for the combined group size. Both generated-proposal analysis and the published-schedule analyzer report undersized room assignments. Room software and equipment remain outside the constraint model until a trusted capability catalog exists.

The Python engine now supports roomless candidates, teacher teams, alternating parity units, profile availability and blocks, subgroup overlap rules, compatible shared lecture units spanning linked groups, and fixed/dated occupancy blockers. The preference compiler is a deterministic local prototype wired to teacher submission and administrator review. It recognizes negated wishes, common weekday inflections, numbered periods before or after the word “пара” (including lists and ranges), ordinal periods through the ninth pair, and explicit even/odd week scope. Day lists joined as conjunctions compile into one typed rule per day; alternative day choices, contradictory week scopes, mixed-polarity wishes, avoid-consecutive wishes, and day-specific consecutive requests remain in review instead of being silently broadened or converted into a different solver rule. Room software wishes are ignored until a trusted capability catalog exists. A generic two-unit consecutive-lessons wish targets any two of the teacher's assigned lesson units; a uniquely grounded subject narrows it to that requirement. Only an exact count of two with a recognized lesson noun becomes the supported consecutive preference. Other counts, ranges, modifiers such as “at least,” ordinal counts, vague quantities, and non-lesson units (such as consecutive days or weeks) stay in administrator review; the solver rewards adjacent lesson pairs but cannot require longer chains. The solver rewards at most one adjacent pair per week parity without multiplying by eligible room combinations. Explicit profile unavailability is a hard blocker; profile availability and approved text-based available/unavailable wishes are soft scoring rules. A text wish that conflicts with hard profile unavailability is flagged for review and withheld. Only approved proposals influence solve scoring; ambiguous and unsupported wishes stay out of the solver. The UI keeps generated proposals private until the administrator explicitly publishes selected rows after review. Editing a weekday, period, eligible room or unit-supported week parity creates a new version of the private proposal and refreshes analyzer findings. Recurring and dated event subgroup changes are validated against their workload split policy; recurring subgroup changes also require balanced paired edits.

The project already has a Hanami scheduling slice with single-requirement recommendations (`RecommendPlacements`, `PlacementStrategy`, `PlacementScorer`), placement validation, `from_recommendation`, schedule event edits, dated transfers and swaps. The new generator should reuse domain identities and validation semantics, but the existing recommendation scorer does not solve all requirements together. Rails remains the administrator UI and Hanami remains the sole owner of schedule data, authorization and publication.

The local service is defined in `apps/scheduler/server.py` and its pinned container in `apps/scheduler/Dockerfile`. It accepts versioned JSON at `/v1/solve`, `/v1/analyze` and `/v1/compile-preferences`, has no database credentials or host-published port, caps request bodies at 8 MiB and permits one CP-SAT solve at a time. Docker Compose places it on a dedicated internal network also attached to Hanami, and limits it to one CPU and 2 GiB. The synthetic solve was exercised over HTTP and returned four placements; this proves the engine boundary only, not correctness against live project data.

## Proposed boundary

Rails starts, monitors and reviews a generation run through Hanami. The administrator chooses an authorized faculty or university scope from the Schedule workspace. Hanami authorizes it, creates a consistent snapshot and durable run record, and starts a bounded scheduler worker. The worker receives a versioned, immutable snapshot and produces a private proposal; it has no direct write access to live schedule tables. A separate Hanami publication operation rechecks scope, revisions and conflicts, then commits the accepted proposal and Outbox records atomically. Existing manual create/PATCH, transfers and swaps remain distinct commands.

Generated cells must live in proposal tables keyed by run ID, owner and authorized scope; a `status` on ordinary `schedule_events` is insufficient because existing queries and other administrator tabs could accidentally see the draft. Public and ordinary admin schedule reads continue to use published events only. The run owner sees a separately labelled sandbox grid and can inspect a diff against the current timetable. Access to a run is checked server-side, including any shared review access explicitly granted later.

The diff compares **logical lesson occurrences**, not only visual weekday/time cells. A recurring event, odd/even parity, subgroup, shared stream, and one-date transfer can occupy the same displayed cell with different meaning. Each changed proposal item records an action (`keep_published`, `use_proposed`, or an explicit administrator edit) and a reason. Red highlighting means an unresolved hard conflict or stale change; amber means a preference violation or missing information. Color is paired with a textual label and a navigable issue list. No individual resolution becomes public immediately. The Publish button is enabled only after the selected proposal passes global validation.

Within the worker, snapshot normalization, constraint compilation, candidate generation, feature calculation, CP-SAT solving, optional decision-model ranking, repair and final validation are modules of one process. Per-candidate network calls would make search latency and failure behavior unpredictable. The model gateway is called only on bounded batches of ambiguous, already feasible candidates and is bypassed when unavailable or unhelpful.

## Scheduling unit and constraint IR

The first compiler stage expands each `study_load_requirement` and its `curriculum_stream`/`student_group_semester` into schedulable lesson units. A unit carries its source requirement, period, duration, recurrence/week parity, subgroup or stream membership, eligible teacher-on-kafedra memberships, eligible rooms, and remaining hours. Expansion must use the project's existing hours and subgroup policies; no invented ID type or synthetic workload record becomes authoritative.

The versioned constraint IR separates:

1. **Hard rules:** required hours and period eligibility; group, teacher and room occupancy; explicit unavailability; room and equipment eligibility where authoritative data exists; already fixed lessons; authorized scope.
2. **Formal preferences:** gaps, early/late periods, compact teaching days, room stability, preferred availability, change distance, and fairness. These become measurable terms of the solver objective.
3. **Semantic preferences:** confirmed, typed preferences whose utility is hard to express precisely. Their source text and parser output are retained, but they may only rank valid candidates and never create a hard rule without an explicit policy decision.

Every IR item needs a stable type, schema version, scope, source record and revision, strength, validity period, actor/provenance and confirmation status. A free-text preference parser may propose IR, but domain validation must ground teacher, room, group, date and period references against authorized records. Ambiguous text becomes a review item. The parser cannot write SQL or mutate schedules.

## Run lifecycle

`requested → snapshotting → solving → validating → proposed | infeasible | failed → accepted/rejected → published`.

The run persists progress checkpoints and a monotonic event sequence. The browser may subscribe to a run-scoped stream or poll `GET /runs/:id` with a cursor to see phase, best feasible score, placed/remaining lesson units, blocking reasons and a preview revision. Progress events are hints; the durable run/proposal rows are authoritative after reconnect. The owner can cancel queued or active generation from the Schedule workspace. Cancellation atomically marks the run terminal, clears its private source snapshot and callback capability, then the worker stops CP-SAT when its next protected progress heartbeat is rejected. Cancellation never writes to published schedule rows. No latency promise is needed for the first prototype, but CPU, memory and concurrent-run limits remain necessary to protect the live API.

Runs are private, server-authoritative records: every administrator, including a super-administrator, can read or edit only runs they requested. Role and schedule scope authorize run creation; they do not grant access to another owner's run. Progress persists under a monotonic `event_sequence`, so polling clients can resume from a cursor and ignore stale responses. Proposal edits use an expected run `revision` and source digest; publication repeats those checks under the placement lock and transaction. The user explicitly withdrew the CRDT requirement on September 30: the administrator must see generation progress after pressing the button. The implementation therefore uses durable server-authoritative progress, automatic polling and revision checks. Concurrent shared-draft merging is outside the current scope. Publication still validates global teacher/group/room constraints atomically.

## Static timetable analyzer

The read-only Hanami analyzer checks collisions in the published recurring schedule and date-resolved occurrences, profile unavailability, room reservations and capacity. The Python analyzer checks each sandbox revision against a snapshot containing workload, teacher/group/room assignments, profile constraints and the same date, parity, holiday, weekday-transfer and dated-event semantics. Draft errors include group/teacher/room clashes, hard profile unavailability, missing required assignments, room capacity and subgroup-hour imbalance. Findings distinguish existing data defects from errors introduced by a proposal. Both analyzers report an unmet approved natural-language wish as a review finding: it explains the trade-off but never turns a soft wish into a hard conflict. Wish-compiler contradictions and ambiguities remain administrator-review findings. Publication repeats final analysis and rejects stale source revisions. Each finding has a stable code, severity, affected occurrence IDs, source constraint and readable Russian explanation. No finding is resolved merely by hiding its mark; the next analyzer revision must verify the edited proposal.

Publication takes an expected proposal revision and expected source revision. The whole proposal revision must first have no unresolved error-severity findings; after that, an administrator may select all or only some rows. Under the existing placement lock and a database transaction, Hanami rechecks the selected proposal against the current source and constraints, applies accepted recurring-event edits in place, applies accepted dated-occurrence edits through the transfer repository, creates accepted generated placements through the domain operation, and writes related audit/Outbox records atomically. The recurring edit retains event IDs, event-batch membership, teachers and additional rooms; subgroup reassignment is accepted only when the selected edits preserve both subgroups' credited hours. Dated edits are currently limited to standalone batches. Batches extending outside the authorized scope cannot be edited. Unselected rows remain private in the proposal. Any stale or invalid result returns a conflict report and leaves the published schedule untouched.

The snapshot includes workload and assignments, teacher constraints, rooms and reservations, time slots, week types and positional parity, academic periods/holidays, recurring events, dated exceptions and transferred days in the requested horizon. It records source revisions, compiler version and objective weights. This makes a run reproducible and allows publication to reject a stale proposal after concurrent edits.

Candidate generation prunes impossible placements cheaply. CP-SAT first maximizes the number of required lesson units placed, then minimizes approved teacher-wish cost, group teaching days and gaps, with earlier periods as the final tie-breaker; workload fairness is deferred. Unplaceable units remain visible as blocking errors in the private draft, and the administrator can try a placement in that sandbox. Any unplaced-unit error or analyzer error blocks publication; after the whole proposal is clean, the administrator may publish all or selected rows. Solves have no fixed wall-clock deadline by default, progress remains visible, and an administrator can cancel an active run. An explicit limit is available for bounded diagnostic runs.

The final validator reconstructs actual date occurrences for the horizon and checks the same API business rules that publication will enforce. A proposal is never published because a model assigned it a high probability. Infeasibility reports should map a small set of blocking facts back to workload, teacher, room and period labels for an administrator; solver internals alone are insufficient.

Candidate pruning now builds a hash index of fixed teacher, group/subgroup and room occupancy once per snapshot, including profile unavailability and room reservations. This replaces a full scan of published lessons and reservations for every candidate slot. An isolated parity check compared the indexed lookup with the previous scan across 648 combinations, including both/even/odd/unknown parity, subgroup overlap, shared teachers/groups, room lists, and reservations. In the pinned scheduler container, 500 lookups against 6,000 unrelated fixed lessons took 2.825 seconds with the scan and 0.001 seconds with the index (about 3,300× for this hot-path microbenchmark). This does not measure total solve time or establish semester-scale latency. The rebuilt scheduler returned an optimal four-placement result on the checked-in synthetic faculty snapshot; no live generation run was queued.

Soft objective contributions from available profile cells and approved available/unavailable wishes are also indexed by teacher/day/period/week parity instead of rescanning every rule for each candidate. The weights remain unchanged. A comparison against the previous calculation matched across 2,160 candidate/team combinations using 1,500 mixed rules. For 12,000 candidates and 1,500 rules, the isolated lookup measured 2.489 seconds by scan and 0.010 seconds indexed (about 257×). After rebuilding, the same synthetic HTTP solve remained optimal with four placements in 0.03 seconds; this small snapshot is a correctness smoke, not a throughput claim.

Teacher-scoped `consecutive_lessons` preferences no longer create a Boolean for every ordered lesson-unit pair. The existing teacher resource `AtMostOne` constraints guarantee that at most one matching lesson can occupy a day/period/parity cell, so the solver can pair adjacent aggregate teacher occupancies instead. Requirement-only preferences keep the original pair formulation because they do not establish teacher exclusivity. In a six-unit synthetic model, variables fell from 1,390 to 620; consecutive-pair variables fell from 840 to 28, with 42 aggregate occupancy variables added. The baseline and optimized models both solved optimally with objective −39 and eight placements in the paired comparison (0.554s vs 0.021s). CP-SAT selected different cell arrangements among tied optima, so this verifies equal objective and feasibility, not identical timetable cells. The rebuilt HTTP service still solved the checked-in synthetic snapshot optimally with four placements. This single controlled model does not establish large-schedule solver performance.

The static analyzer now indexes lessons by weekday/period and shared teacher, group or room, then examines only candidate pairs that share at least one resource. Its existing date-occurrence, parity, subgroup, event-batch and staged-transfer exclusions still run before findings are emitted. Output matched the prior analyzer exactly for the checked-in scenario and for 25 randomized snapshots of 72 mixed recurring, dated and proposed events each. An intentionally sparse-resource stress case with 2,500 events all in the same weekday/period took 10.035 seconds before indexing and 0.018 seconds after, with zero findings in both results. This isolates pair-search cost and is not a broad runtime or schedule-capacity guarantee.

Generation now checks the worker lease-cancellation signal during fixed-snapshot indexing and candidate/model construction, as well as before and after solve validation. A worker that has lost its lease returns `GENERATION_LEASE_LOST` without continuing to build a stale model or returning a proposal. The existing solver-search cancellation monitor remains active. A controlled cancellation smoke triggered both during occupancy indexing and during candidate construction and got an empty `unknown` result in both cases; an uncancelled synthetic solve remained optimal with four placements. This improves stale-worker cleanup, not the database lease or retry protocol itself.

## Teacher preference compiler

Teachers submit wishes in Russian free text, scoped to their own identity and a selected semester. The compiler returns proposed versioned JSON rules and review findings, never a direct schedule mutation. The current implementation uses deterministic Russian templates only; it does not call Jev or another language model. Any later local model must emit the same restricted rule schema, pass schema and domain validation, and remain in shadow mode until it is measured against frozen wishes. Domain grounding resolves named subjects, activity types, weekdays and periods against authorized reference data. Heater/oven wording is a reason, never an inferred subject name. An unnamed two-unit consecutive wish is scoped to the teacher, even when that teacher has multiple requirements. A uniquely named subject scopes the wish to one matching requirement; a named subject with zero or multiple exact matches, or no semester workload, stays in review. The compiler stores the original text, parsed proposal, grounded IDs, ambiguity findings, compiler version and review outcome. Corrections form new wish records so a past scheduling run remains reproducible.

The supported JSON vocabulary is deliberately small: `unavailable_slot`, `available_slot`, and `consecutive_lessons`. Slot rules carry `scope`, `weekday`, `slots`, `strength`, `status`, and `source`; consecutive rules carry `scope`, `pair_count`, `strength`, `status`, and `source`. These free-text rules are soft. Profile unavailability is a separate hard constraint, and contradictory wishes produce a review finding without a proposed rule. The compiler cannot promote free text to a hard rule on its own. Unsupported wishes remain visible for manual review; room software/equipment wishes are retained as teacher text and marked for administrator review, but they do not become constraints until a trusted room capability catalog exists.

Example (current compiler output):

```json
{
  "schema_version": 1,
  "type": "unavailable_slot",
  "scope": {"teacher": "42"},
  "weekday": "monday",
  "slots": ["p1", "p2"],
  "strength": "soft",
  "status": "proposed",
  "source": "wish-uuid"
}
```

Two known examples are: “I want two consecutive lessons because the oven is already on,” and “I want a room with particular software installed.” A generic consecutive-lessons wish remains teacher-wide even when the teacher handles several requirements. A uniquely named subject grounds the rule; a named but unmatched subject remains in review. A teacher with no requirements in the selected semester cannot create a no-op preference. Room software/equipment matching is deferred: retain the text and add a review finding, but do not compile it into a scheduling constraint until a trusted room capability catalog exists. Teacher text may also say they cannot teach Monday periods 1–2; once approved, this is a soft wish. Existing hard profile unavailability still blocks a lesson, and an opposing text request to schedule during that block is sent to administrator review. The parser never silently overrides a hard profile rule.

The current approval path is restricted to a super-administrator. Parsed meaning, grounded entities and discrepancies are shown in Russian before activation; the compiler never activates its own proposals. If a new typed available/unavailable slot wish contradicts another active wish from the same teacher for an overlapping weekday, period and week parity, the new rule is withheld and sent to administrator review; an existing approved wish is left intact. Approval repeats the contradiction check inside a PostgreSQL transaction while holding a per-teacher advisory lock, preventing two pending conflicting wishes from being approved concurrently. A super-administrator can withdraw a prior approval, after which the teacher can submit the clarified wish again. At generation time, an approved wish whose teacher/load context or compiler version is stale is returned to administrator review and excluded from the solver until recompiled and approved again. Opposite even/odd week rules remain compatible. Hard profile unavailability stays authoritative; an available profile slot does not erase a soft wish to avoid that time, and an unavailable profile slot blocks an opposing text wish. Negated avoidance language is routed to review instead of being mapped to a slot rule. Compiler `russian-templates-v31` recognizes explicit negative weekday/period forms such as “предпочитаю не проводить занятия” and “нежелательна первая пара”; double negatives followed by modal verbs and infinitives, unsupported or contradictory phrasing remain review-only. Alternative period choices (“first or second pair,” including slash-separated forms) now go to review rather than becoming a preference for both or only one slot; conjunctions and explicit ranges remain supported. Consecutive requests are compiled only when the count is exactly two: inflected digits (such as “2-х”) are accepted as two, while other inflected numbers, fractions (“two and a half”), ranges, qualified quantities and counts of non-lesson units (days, weeks, semesters, periods or shifts) remain in review. Calendar-specific weekdays (for example, the first Monday of a month), multiweek cadences, and intervals relative to a lesson period (including “not earlier/later than the third period”) are review-only because the rule schema cannot represent them. Optional boundary wording such as “not earlier than on/at the third period” also remains review-only even when punctuation or explanatory words separate the boundary phrase from the period. Explicit conditional or exception clauses are sent to review because the rule schema cannot represent them; the compiler must not silently make such wishes unconditional.

## Planned administrator teacher workload tab

The administrator Teachers workspace now has a separate semester-scoped workload tab for the selected teacher. It lists that teacher's assigned lesson requirements, student groups, activity types, assigned/actual/remaining hours and current room assignments, with an empty state when the teacher has no assignments in that semester. Room changes open the existing assignment editor scoped to the requirement's department, preserving the complete teacher and room assignment collections.

The workload tab implementation reuses the existing admin workload read gateway and room-assignment editor. A requirement-specific department editor can be opened without a faculty selector because server authorization scopes the write to the actual requirement's department. Room choice stays searchable, and saving preserves all selected teachers and rooms. Wish authorship is resolved: the teacher submits through the teacher cabinet; the administrator reviews. The tab links to the existing semester wish-review workflow filtered to the selected teacher. The admin wish-list response now carries its teacher ID so this filter is stable and does not depend on names. Reuse `BuildTeacherPreferenceContext`, `CompileTeacherWish`, and the existing wish-review workflow; do not add a second parser or schedule-write path, and retain the explicit review/approval gate for parsed wishes.

The Hanami boundary now validates the scheduler response before persisting it: only schema version 1 `available_slot`, `unavailable_slot` and `consecutive_lessons` rules are accepted; rules must remain `soft` and `proposed`, identify the submitting teacher and source wish, use known day/week/period values, and ground subject-scoped consecutive rules to that teacher's semester workload. Teacher-wide consecutive rules require at least one semester workload. The authorized compiler context includes the current `pN` time-slot catalog in its fingerprint; a period number absent from that catalog becomes an unsupported review finding instead of an approved no-op. Findings must use the review-only compiler vocabulary and refer only to the submitted wish. Unknown fields, rule types, empty responses, cross-teacher scopes and unsupported hard rules fail closed as an invalid scheduler response.

Approved-preference solver check (2026-09-29): the live scheduler container solved the frozen synthetic snapshot twice with the same deterministic seed, once with its approved `consecutive_lessons` preference and once without it. With the preference, the two grounded laboratory units were placed in adjacent periods on Thursday; without it, they were placed on separate days. Both runs were optimal, while profile contradictions remained review findings in both. This confirms the approved wish changes the soft objective without relaxing hard profile constraints. This is one synthetic smoke check, not a quality benchmark.

## Optional model-guidance state builder (deferred)

This separate model-input builder is not part of the current scheduler. The required teacher-wish compiler is the deterministic natural-language-to-JSON pipeline described above; it does not require model state, questions or candidate scoring. If a local decision model is adopted later, its input should be a pure, versioned function over a snapshot, a lesson unit and bounded candidate IDs. It should emit compact structured state, fixed answer sets and deterministic features, exclude credentials and unrelated free text, and record input hash, model/checkpoint version, output distribution, latency and fallback reason. Model probabilities must never be treated as verified constraint satisfaction.

## Local model decision
TypeSafe's [official quick start](https://docs.typesafe.ai/introduction/quickstart), rechecked on 2026-09-29, sends requests to `https://api.typesafe.ai/v1/systemone` with a bearer API key and documents an SDK client that calls `jev-latest`; the [official API reference](https://api.typesafe.ai/docs) is the service endpoint's reference. The [Jev announcement](https://typesafe.ai/blog/introducing-system-one-models-and-jev) describes that hosted service as early access. The official materials reviewed here do not document a downloadable TypeSafe checkpoint or an official local inference runtime.

There is now a third-party local implementation worth evaluating: [`amithgc/local-jev`](https://github.com/amithgc/local-jev) exposes a Jev-compatible `/v1/systemone` API and is MIT-licensed. Its README calls it a research project and reports 80.5% on the 231-item JevBench for `llm-qwen3.5-4b` versus the published 86.6% hosted Jev result. These are the project's general benchmark figures, not Russian scheduling results. The default Qwen model is listed at 9.32 GB on disk and about 8.5 GB memory; smaller options trade accuracy for footprint, while its 0.87 GB NLI model reports 54.1% on JevBench. The package declares broad, unpinned `torch` and `transformers` dependencies. A separate compatible implementation, [`us/jev-local`](https://github.com/us/jev-local), also exists, but its default scorer is explicitly a deterministic contract baseline rather than an intelligent model. ## Run snapshot retention

Generation snapshots can contain teacher availability, workload assignments, and natural-language wish data. Keep the immutable snapshot only while the run is queued, processing, or still has an unpublished proposal. Once a run reaches a terminal state with no publishable proposal (`published`, `infeasible`, or terminal `failed`), replace the snapshot with an empty JSON object while retaining status, findings, source digest, and audit metadata. Retries retain the snapshot; a proposed run retains it until the last publication batch succeeds. This limits sensitive-data retention without expiring an administrator's private draft. The worker's idle queue scan selects only run IDs; it fetches the full snapshot only after claiming a run. Routine SQL logs are suppressed in that worker process while warnings and errors remain enabled.

## Best-effort drafts — 2026-09-29

The solver now maximizes the count of placed required lesson units before optimizing approved soft preferences and period costs. A conservative coefficient bound makes that priority lexicographic: no improvement in secondary cost can outweigh one additional placed lesson. Unplaced units remain visible as `UNPLACED_REQUIRED_LESSON` errors with their workload identity, and the API persists the feasible placements as a proposed private draft. Any such error blocks all publication, including selected rows, through the existing server-side finding check and final reanalysis. The error card lets an administrator choose a day, period, parity and eligible room to add that unit to the private proposal; the API checks scope, run revision, source digest and lesson-unit parity, then reruns whole-proposal analysis. It removes only the matching unplaced-unit error, preserves other omitted units, and exposes any new placement conflict through the existing editor workflow.

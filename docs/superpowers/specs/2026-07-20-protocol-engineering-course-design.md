# Design: курс «Проектирование mesh/DTN-протоколов — от нуля до собственного протокола»

Дата: 2026-07-20

Статус: согласованный дизайн, ожидает ревью записанного документа

Язык курса: русский; термины, имена API и цитируемые первичные источники сохраняют оригинальные английские обозначения

## 1. Цель

Создать в отдельной директории `course/` самостоятельную учебную систему объёмом примерно 160 часов обязательного материала и до 40 часов адаптивных углублений. Курс должен привести человека с приблизительным знанием модели OSI и без знания Rust к способности самостоятельно:

1. сформулировать требования и ограничения нового сетевого протокола;
2. связать решения с физическими, энергетическими и платформенными пределами;
3. выбрать архитектуру, wire format, state machines, routing, synchronization и security model;
4. построить количественную модель и симулятор;
5. реализовать проверяемый прототип на Rust;
6. найти слабые места посредством failure analysis, adversarial tests и design review;
7. защитить принятые компромиссы и честно описать остаточные риски.

`mesh_milk` служит сквозным case study, но не единственным правильным ответом. Целевая пропорция содержания: 60% переносимых принципов проектирования протоколов и 40% анализа спецификации и реализации `mesh_milk`.

## 2. Границы

### Входит в первый релиз

- выполнение всех обязательных лабораторных на одном обычном ПК;
- модель радиоканала и BLE на уровне, необходимом для инженерных оценок;
- DTN/store-and-forward, opportunistic routing, reconciliation и распределённое состояние;
- прикладная безопасность и использование стандартных криптографических примитивов;
- wire formats, canonical encoding, parser hardening и state machines;
- Rust, необходимый для протокольного кода: ownership, borrowing, enums, traits, errors, generics, async concepts, serialization, testing, fuzzing и вводное понимание `no_std`;
- моделирование контактов, пропускной способности, хранения, задержки и энергетических proxy-метрик;
- управляемый проект `mini_milk` и самостоятельный capstone-протокол.

### Не входит в первый релиз

- лабораторные на реальных Android/iOS BLE API;
- работа с nRF52, ESP32 или другим embedded-оборудованием;
- полный общецелевой курс Rust;
- создание новых криптографических примитивов или формальные криптографические доказательства исследовательского уровня;
- заявление о production readiness без испытаний на реальном радио и целевых ОС.

Эти ограничения явно сообщаются ученику. Модели ПК не должны выдаваться за экспериментальное подтверждение поведения реального BLE-оборудования.

## 3. Предварительный аудит источника истины

Перед написанием учебных модулей выполняется трассируемый аудит:

1. полностью прочитать `specification/01`–`specification/18`, исследовательские материалы и bibliography;
2. изучить публичные границы crate-ов и существенные реализации в `implementation/mesh-milk`;
3. построить матрицу `требование спецификации → реализация → тест/вектор → статус`;
4. выявить расхождения, provisional-константы, открытые вопросы и решения, изменённые реализацией;
5. зафиксировать Git revision, относительно которой написана версия курса;
6. не изменять нормативную спецификацию ради удобства курса; обнаруженные проблемы оформлять отдельно для последующего решения владельцем проекта.

Наличие документов 16–18 означает, что фактический объём уже превышает исходную карту из 15 документов. Они входят в аудит; в обязательное ядро курса попадают только необходимые понятия, остальные используются как специализации или case studies.

## 4. Архитектура обучения

Выбрана спиральная инженерная программа. Каждая существенная тема возвращается на трёх уровнях:

1. интуитивная и физическая ментальная модель;
2. количественная модель с явными допущениями;
3. реализация, эксперимент и критический разбор.

Повторяющийся цикл модуля:

`физический смысл → модель и расчёт → mesh_milk case → Rust lab → атака/отказ → проверка`

Rust изучается гибридно: короткий фундамент появляется до сложного протокольного кода, а последующие конструкции языка вводятся непосредственно перед задачей, где они нужны. Курс обещает рабочую отправную точку для дальнейшего изучения Rust, а не полное владение языком.

## 5. Учебные блоки и бюджет времени

Точные названия уроков определяются в implementation plan, но дизайн фиксирует следующие блоки:

| Блок | Основное содержание | Ориентир |
|---|---|---:|
| 0. Вход и инструменты | инженерное мышление, Git, CLI, биты, hex, тестовый цикл | 8 ч |
| 1. Физика связи | радиоканал, шум, link budget, BLE, airtime, энергия | 15 ч |
| 2. Сетевой фундамент | layering, framing, addressing, reliability, congestion | 15 ч |
| 3. Rust I | ownership, borrowing, data modeling, enums, traits, errors | 17 ч |
| 4. DTN и routing | contact graphs, store-and-forward, quotas, epidemic и spray-подходы | 20 ч |
| 5. Sync и состояние | set reconciliation, Bloom filters, DAG, causal order, CRDT concepts | 18 ч |
| 6. Security и crypto | threat model, identity, handshake, AEAD, metadata, group trade-offs | 20 ч |
| 7. Rust II и robustness | async concepts, codecs, state machines, fuzzing, simulation, `no_std` overview | 17 ч |
| Capstone | самостоятельная спецификация, модель, прототип, adversarial evaluation и защита | около 30 ч |

`mini_milk` не является отдельным блоком в конце: он накапливается вертикальными срезами внутри блоков 2–7 и требует ориентировочно 30 часов уже учтённой практики. Блоки 0–7 составляют около 130 часов вместе с этой практикой; capstone добавляет около 30 часов. Итоговое обязательное время допускает уточнение после декомпозиции уроков, но целевой ориентир — 160 часов. До 40 часов адаптивных математических и исследовательских углублений доводят полную траекторию примерно до 200 часов.

## 6. Адаптивная математика

Обязательный путь предполагает школьную математическую базу. Каждая формула сопровождается:

- смыслом величин и единиц измерения;
- выводом или доступной мотивацией;
- примером расчёта;
- проверкой размерностей и порядка величины;
- указанием границ применимости модели.

Углубления покрывают вероятностные модели, графы, линейную алгебру для coding techniques, статистическую интерпретацию симуляций и более строгий анализ сложности. Ученик может пройти ядро без углублений, но capstone всё равно требует количественно обосновать собственный дизайн.

## 7. Структура артефактов

```text
course/
├── README.md
├── ROADMAP.md
├── competencies.md
├── modules/
├── rust-track/
├── labs/
├── projects/
│   ├── mini-milk/
│   └── capstone/
├── assessments/
├── references/
├── glossary/
└── instructor/
```

Материалы ученика не раскрывают решения преждевременно. `instructor/` содержит решения, рубрики, типичные ошибочные ответы, градуированные подсказки и рекомендации по проверке. Starter-код, тесты и симуляторы располагаются рядом с соответствующими лабораторными либо проектами; точная граница определяется планом реализации.

## 8. Контракт учебного модуля

Каждый модуль обязан содержать:

1. измеримые результаты обучения и prerequisites;
2. инженерную мотивацию и физический смысл;
3. понятную ментальную модель;
4. количественную модель и адаптивное углубление, где оно уместно;
5. первичные источники и границы их применимости;
6. трассировку к конкретным разделам `mesh_milk` и, где уместно, к Rust-коду;
7. лабораторную работу с воспроизводимым результатом;
8. сценарий отказа, атаки либо ошибочного предположения;
9. quiz или design questions, deliverable и rubric;
10. критерий готовности к следующему модулю;
11. краткое резюме и дальнейшее чтение.

## 9. Доказательность и цитирование

Существенные утверждения маркируются по смыслу:

- `[FACT]` — утверждение подтверждено указанным источником;
- `[MODEL]` — полезное упрощение с перечисленными допущениями;
- `[DESIGN]` — инженерное решение и его trade-offs;
- `[HYPOTHESIS]` — проверяемое, но ещё не подтверждённое предположение.

Предпочтение источников: peer-reviewed papers, RFC и официальные спецификации, официальная документация проектов, затем качественные вторичные объяснения. Ссылки проверяются по реально открытым URL. Для каждого крупного решения приводятся rationale, альтернативы, trade-offs и evidence basis. Курс ведёт собственный реестр источников; изменения нормативной спецификации дополнительно обязаны соблюдать общий `specification/research/bibliography.md`.

Краткость объяснения имеет приоритет над количеством цитат: источник подтверждает модель, но не заменяет педагогическое объяснение. Прямые цитаты используются минимально; основная форма — точный пересказ с ссылкой.

## 10. Два проекта

### Проект A: `mini_milk`

Управляемый учебный протокол с заранее ограниченными требованиями:

- DTN/store-and-forward;
- BLE-подобный контактный транспорт в симуляторе;
- компактный canonical wire format;
- идентичности и базовая аутентифицированная конфиденциальность на стандартных primitives;
- copy budget, TTL и quota;
- простое reconciliation;
- deterministic simulation, negative tests и fuzz targets.

Проект строится вертикальными срезами. После каждого среза два симулированных узла должны демонстрировать новое end-to-end поведение.

### Проект B: самостоятельный capstone

Ученик выбирает сценарий и проектирует новый мини-протокол. Разрешено наследовать идеи `mesh_milk`, но запрещено без обоснования копировать его решения. Обязательные результаты:

- requirements, non-goals и threat model;
- RFC-like specification с wire format, FSM, invariants и error behavior;
- количественная модель;
- Rust-прототип как минимум двух взаимодействующих узлов;
- deterministic и adversarial tests;
- анализ альтернатив и residual risks;
- письменная или устная защита.

## 11. Система оценивания

Оценивается лестница самостоятельности:

1. **объяснить** концепцию и её физический смысл;
2. **рассчитать** пределы и бюджеты;
3. **реализовать** минимальное корректное поведение;
4. **сломать** собственное решение тестом, атакой или отказом;
5. **защитить** выбор, альтернативы и остаточные риски.

После каждого модуля выполняются concept quiz, расчёт, Rust-deliverable, failure/adversarial exercise и запись в engineering journal. Предусмотрены пять ворот:

- Gate A — wire format и contact simulator;
- Gate B — `mini_milk` end-to-end;
- Gate C — adversarial и scale review `mini_milk`;
- Gate D — capstone design review до реализации;
- Gate E — воспроизводимая реализация и защита.

Выпуск возможен только если ни одна критическая категория capstone rubric не провалена. Прототип должен воспроизводимо работать на обычном ПК; ученик должен объяснить пределы модели и уметь аргументированно отклониться от решений `mesh_milk`.

## 12. Обработка ошибок обучения

- Ошибочный ответ сопровождается диагностикой модели мышления, а не только правильным результатом.
- Подсказки выдаются ступенчато: направление → релевантный принцип → частичная структура решения.
- Лабораторная должна различать ошибки окружения, Rust/compiler errors, ошибки протокольной логики и неверные инженерные допущения.
- Все примеры команд содержат ожидаемый результат и способ восстановить чистое состояние без удаления пользовательской работы.
- Если симуляция не подтверждает гипотезу, курс учит пересматривать модель; результат не подгоняется под спецификацию.

## 13. Проверка качества курса

Для каждого релиза курса выполняются:

- автоматическая проверка ссылок и локальных cross-references;
- сборка и тестирование всего starter/reference Rust-кода;
- запуск deterministic simulations с фиксированными seeds;
- проверка соответствия лабораторных рубрикам;
- матрица покрытия компетенций модулями и gates;
- аудит терминов по glossary;
- adversarial persona review крупных выводов в формате `Potential flaw / Alternative / Resolution`;
- проверка того, что решения преподавателя не доступны из пути ученика случайно;
- пилотное прохождение или dry run с фиксацией фактического времени.

Критические расхождения между курсом, спецификацией и реализацией блокируют утверждение соответствующего модуля до явной маркировки расхождения.

## 14. Версионирование и обновление

Каждый релиз курса указывает:

- Git revision спецификации и реализации;
- дату последней проверки внешних источников;
- совместимую версию Rust toolchain;
- известные расхождения и устаревшие уроки.

Обновление спецификации не должно молча менять смысл старого учебного материала. Существенные изменения получают migration note и обновление трассировочной матрицы.

## 15. Критерии готовности первого полного релиза

Первый полный релиз считается готовым, когда:

1. все обязательные модули удовлетворяют контракту раздела 8;
2. обязательная траектория покрывает каждую заявленную компетенцию;
3. `mini_milk` проходит свои end-to-end, negative, adversarial и fuzz-проверки;
4. capstone содержит задание, шаблоны, rubric и один эталонный пример без навязывания единственной архитектуры;
5. весь курс воспроизводимо проходится на обычном ПК;
6. источники проверены, а `[FACT]`, `[MODEL]`, `[DESIGN]`, `[HYPOTHESIS]` используются последовательно;
7. выполнен dry run и уточнён фактический бюджет времени;
8. отсутствуют незаполненные обязательные разделы и неразрешённые внутренние противоречия.

## 16. Следующий этап

После ревью этого дизайна создаётся подробный implementation plan. Он должен сначала декомпозировать аудит спецификации и реализации, затем определить карту компетенций и только после этого планировать написание модулей, лабораторных и проектов. Написание курса до завершения аудита и карты компетенций не допускается.

# Rails migration and architecture execution plan

Status: active. Updated 2026-09-07. This plan extends the August public-page migration; it does not replace the full React-to-Rails objective.

## Requirements and working rules

- Migrate every React user flow to `apps/schedule_web`, retaining Hanami API ownership of business data.
- Keep Rails controllers thin; separate HTTP actions, dry-validation contracts, dry-monads operations, API gateways, policies, entities, and presenters. Database repositories and migrations remain in the API; Rails must not bypass API authorization with direct SQL.
- Russian interface, English progress reports. Build searchable entity selection, contextual suggestions, and accessible drag-and-drop; avoid large dropdowns.
- Preserve the completed Excel migration worker. Do not add tests. Use syntax, framework checks, live requests, browser walkthroughs, and independent code review.
- After each coherent implementation batch, ask a review agent to inspect behavior, security, and design. Fix findings with up to three attempts; record unresolved findings in `docs/agent-reviews/` and proceed to independent work.
- Delete `apps/frontend` only after the full parity matrix has current runtime evidence. Preserve unrelated working-tree changes and nested Git repositories.
- Future infrastructure requirements are tracked in [the architecture roadmap](../../architecture/2026-09-06-runtime-and-platform-roadmap.md). Experiments and planned deployment are not evidence of implementation.

## Ordered implementation

1. **Resilience foundation.** Route auth mutations through an uncached, non-retrying timeout/breaker boundary. Complete cold-start breaker discovery. Prevent arbitrary exception text entering shared upstream failure logs. Verify syntax/autoload, dependency availability, and independent review; exercise outage/recovery when runtime returns. Follow up with atomic half-open breaker semantics and service-wide protection after reviewing concurrent calls.
2. **Detailed API/React capability map.** Read each remaining component and all API route groups/contracts/policies. Record fields, mutations, permissions, pagination, errors, and side effects. Separate missing UI from missing backend behavior. Include existing constraints rather than implementing a duplicate model.
3. **Authenticated foundation and password change.** Route authenticated accounts to their allowed workspace; support required password rotation. Add small actions, permission policies, validated input and status-aware gateway responses. Check session fixation, CSRF, token refresh concurrency, cache isolation and failure behavior.
4. **Admin shell and searchable reference data.** Preserve chosen semester/group in URLs. Establish consistent action placement, readable tables, inline validation and keyboard-operable paginated entity search. Port all reference and account operations. Check desktop/mobile layouts and role restrictions against the API.
5. **Teacher workspace and constraints.** Port self-service and administrator teacher screens. Make time constraints understandable as a weekly grid with clear validity dates and reasons. Enforce department/faculty boundaries server-side. Distinguish availability constraints from preferences in recommendations.
6. **Workloads and schedule builder.** Put unscheduled workload beside the week grid. Suggest suitable teacher/room/slot based on API constraints. Provide DnD plus click/keyboard placement, contextual editing, atomic swap, clear conflict explanations and confirmation for destructive changes. Preserve multi-group streams, subgroup, alternate-week and specific-date semantics. Measure a representative full-group scheduling walkthrough; the usability goal is minutes, not merely exposed CRUD.
7. **Remaining staff screens.** Port overview, notices, calendar/frozen-date operations and account management with complete parity. Add audit visibility where the authorized API already supports it. Review all large selectors and dense layouts for ergonomic improvements.
8. **Observability and durable work.** Implement the roadmap's Fluentd/Loki/Grafana/Prometheus stack, JSON event schema, protected audit view and operating runbooks. Inspect existing Outbox transaction boundaries and delivery semantics before extending them. Add bounded batch workers and recovery paths without touching the completed Excel workflow.
9. **Measured infrastructure experiments.** Evaluate Solr, graph-based recommendations and Protobuf in isolated profiles/data. Produce measured decisions. Design command/query repository separation, read-your-writes routing and PostgreSQL failover separately; rehearse on disposable storage before changing the live database topology.
10. **Full verification and React removal.** Walk every inventory row with real API data at desktop/mobile sizes and with keyboard navigation. Verify role boundaries, failed/stalled dependencies, request deadlines, mutations, cache isolation, accessibility and asset/CSP behavior. Record unresolved limitations accurately. Once all required React flows are proved, remove the React directory, Compose service, stale build/deployment references and documentation references; validate Rails-only Compose/build/navigation again.

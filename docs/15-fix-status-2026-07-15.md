## 1. `schedule_events#from_recommendation` multi-owner scope resolution — FIXED, verified live

Handoff §2's deferred gap: the payload's `load_requirement_ids[]` can span several kafedras'
load, which `ScopeResolver`'s single-owner-with-ANY-semantics can't safely resolve — the
endpoint was reachable only by `scheduler` (unconditional) and `super_admin`, locking out a
scoped `kafedra_admin`/`faculty_admin` accepting their own recommendation.

`ScopeResolver#multi_owner_groups(resource, params)` (`slices/admin/authorization/scope_resolver.rb`)
resolves one owner list per `load_requirement_id` for `"schedule_events"` payloads shaped
like `from_recommendation`'s, returning `nil` for every other resource/action (so the normal
single-group path is untouched). `Authorizer#authorize!` now checks `groups.all? { tier-check }`
when groups are present — the caller must pass the tier check against **every** referenced
load requirement, not just one, mirroring the ALL-of-scope semantics the handoff asked for
(same spirit as `study_load_requirements#update`'s existing `stream_relink_forbidden?` guard).

**Live verification** (probe `kafedra_admin` scoped to kafedra 1):
- All-in-scope recommendation (kafedra 1 only) → authorization passes, reaches real
  placement-conflict logic (`409 slot_taken` on a contested room — not `403`).
- Out-of-scope recommendation (a load requirement from kafedra 57) → `403 {"error":"forbidden"}`.
- **Mixed** recommendation (one in-scope + one out-of-scope load requirement) → `403` — confirms
  ALL-of, not ANY-of, semantics; a scoped admin can't smuggle an out-of-scope id in alongside a
  legitimate one.
- `super_admin` with the same out-of-scope payload → not blocked (reaches business logic),
  confirming no regression to the unconditional bypass.

## 2. `Policy` module comment/code inconsistency — RESOLVED AS DOCUMENTED DECISION

Handoff §3: the comment above `curriculum_streams`/`study_load_requirements`/
`teaching_assignments` in `slices/admin/authorization/policy.rb` said kafedra_admin "cannot
create or delete load structures (faculty_admin / scheduler handles that)", but

unilaterally widening access), the comment was corrected to match the code rather than granting
scheduler a new write privilege without product sign-off. No behavior change.

## 3. `GET /admin/kafedras/:id/curriculum_streams` (+ 3 siblings) 500 — FIXED, verified live (new finding)

Found while constructing the live test for item 1: `Serializers::CurriculumStreams::Index`
requests a deeper `include:` graph (the full `study_load_requirements.teaching_assignments...`
chain) than `CurriculumStreamRepo#aggregate_details` actually combined from the DB (it borrowed
the narrower `CurriculumStreamPresenter.combine_graph`, which stops at `study_load_requirements`).
`StudyLoadRequirementSerializer`'s own `lazy_load_data: true` comment on `teaching_assignments`
explains this exact failure mode: that flag only prevents `ROM::Struct::MissingAttribute` when
the caller *doesn't* ask for the association — this serializer does, unconditionally.

Fix: `Serializers::CurriculumStreams::Index::INCLUDE_PATHS` is now the single source of truth
(the constant the serializer already needed), and `CurriculumStreamRepo#aggregate_details`
combines from it instead of the narrower presenter graph — no more drift between what's
requested and what's fetched. Affects (and fixes) 4 endpoints that all share this serializer +
repo method: `GET /admin/kafedras/:id/curriculum_streams`,
`GET /admin/student_group_semesters/:id/curriculum_streams`,
`GET /admin/student_group_semesters/:id/load`, `DELETE .../:id/load` (`load_destroy`).

**Live verification**: all four confirmed working (200, full teaching_assignments/
teacher_on_kafedra/assignment_room_references/room graph present in the response) post-rebuild.
Regression-checked plain `GET /admin/curriculum_streams` and `GET /admin/faculties` — unaffected
(200, unchanged shape), since `CurriculumStreamPresenter.combine_graph` itself wasn't touched.

## 4. `schedule_events#from_recommendation` returned 500 on a *successful* write — FIXED, verified live (new finding)

Found live-testing item 1's happy path: the event was actually created (confirmed via DB —
`event_outbox` insert + commit logged), but the HTTP response then crashed with
`ROM::Struct::MissingAttribute: undefined method 'room'`. `CreateScheduleEventForStream`
returned the bare struct from `se_repo.create(...)` (only the just-inserted columns) straight
to `ScheduleEventPresenter`, which declares a full `includes "room", "time_slot", ...` graph
that was never combined — silently worse than a normal 500, since the client sees a failure for
a request that actually succeeded. The sibling `Actions::ScheduleEvents::Create` action already
had the correct pattern (its own comment: `repo.fetch(event.id) # re-fetch with full aggregate
graph`) — `CreateScheduleEventForStream` just never got it.

Fix: one line — the operation now returns `se_repo.fetch(ev.id)` instead of the bare `ev` for
each created event.

**Live verification**: `POST /admin/schedule_events/from_recommendation` with a genuinely free
slot → `201` with the full JSON:API payload (room/time_slot/week_type/study_load_requirement/
event_teachers all present in `included`), not a 500. Test event deleted after verification via
`DELETE /admin/schedule_events/:id` (204); no lasting data change.

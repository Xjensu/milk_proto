Context: `docs/security-review-2026-07-12.md` and `docs/production-readiness-roadmap-2026-07-12.md`
were fully triaged and the P0/P1 blockers plus most P2/P4 items were fixed and live-verified —

## 1. Add regression coverage for the fixes in `docs/13-fix-status-2026-07-13.md`

Everything in that doc was verified by hand against a live stack, not by an automated test
suite. Before this code is touched again, it's worth locking these down, roughly in order of
how expensive a silent regression would be:

- **`Authorizer#authorize!` reassignment guard** (§3.1) — one test per affected resource
  (`teacher_on_kafedras`, `kafedras`, `curriculum_streams`, `study_load_requirements`,
  `teaching_assignments`): scoped account PATCHing a reassignable FK to an out-of-scope
  target → 403; same account PATCHing a non-FK field on the same row → 200. This is exactly
  the roadmap's own original ask ("Add a regression test per affected resource") and is the
  highest-value test to have, since this is the one finding the review called a live,
  reproducible privilege escalation.
- **`ContractRunner#oversized_array_path`** — a contract with an undeclared array key >500
  elements → 422 before any DB/business logic runs (assert on timing or a mock to prove
  `contract.call` was never invoked, not just on the status code).
- **`StreamTicketStore`** — ticket redeemed once succeeds, second redemption of the same
  ticket fails; ticket past its TTL fails.
- **`PasswordPolicy.weak?`** — table-test the boundary (all-digits, all-letters, 7-char
  otherwise-valid, exactly 8-char valid) across all three contracts that use it.

## 2. `schedule_events#from_recommendation` multi-owner scope resolution (deferred from this pass)

Flagged in `docs/13-fix-status-2026-07-13.md`'s P4 write-up: this action's payload carries
array-shaped id fields (`load_requirement_ids[]`, `teacher_on_kafedra_ids[]`,
`group_semester_ids[]`) that can belong to different kafedras/streams. `ScopeResolver`'s
owner-chain helpers (`owners_for_load_requirement`, etc.) all assume a single id. Right now
this endpoint is reachable by `scheduler` (unconditional under the SCHEDULE tier) and
`super_admin` — an improvement over the pre-fix state (was GLOBAL-only) but not the full
fix, since a scoped `kafedra_admin` accepting a recommendation for their own kafedra's slot
still can't reach this endpoint.

**Suggested approach**: extend `ScopeResolver` with a method that resolves owners for *each*
id in `load_requirement_ids` and requires the caller to own *all* of them (not just one —
accepting a recommendation that spans several kafedras' load should require scope over all
of them, mirroring how `study_load_requirements#update`'s `stream_relink_forbidden?` already
handles a similar single-field cross-kafedra check). This is a genuine authorization-model
extension, not a one-line fix — budget it as its own reviewed change, not a quick patch.

## 3. `Policy` module comment/code inconsistency (noticed, not fixed — out of scope for the review's own findings)

`slices/admin/authorization/policy.rb`'s comment block above `curriculum_streams`/
`study_load_requirements`/`teaching_assignments` says: *"kafedra_admin may update load...
but cannot create or delete load structures (faculty_admin / scheduler handles that)"* —
but the actual `WRITE_MATRIX` entries are `{ create: FACULTY, update: KAFEDRA, delete: FACULTY }`,
and `FACULTY` tier's `faculty_writer?` only checks `account.faculty_admin?` — there is no
`scheduler` branch. So today, `scheduler` accounts **cannot** create/delete load structures,
contradicting the comment's stated intent.

This wasn't in either source doc, so it wasn't touched during the fix pass — flagging it
here as a genuine ambiguity needing the same kind of explicit decision the roadmap asked for
elsewhere (P4's `:write` bug): either update the comment to match the code (scheduler
doesn't get this), or add a `scheduler` branch to `faculty_writer?` (or a dedicated check)
to match the comment's intent. Don't guess — this is a real product decision.

## 4. P3 — infrastructure/operations (not code; explicitly deferred by this pass's operating constraints)

All of these require touching `docker-compose.yml`, `deploy/nginx/nginx.conf`, or
environment/secrets configuration, which was out of scope for the fix pass (existing configs
were treated as working and not to be modified without explicit instruction). None of them
are code defects — they're deployment decisions that need to be made deliberately:

- **Network topology**: confirm production doesn't expose `api_geteway`'s host port (2300 in
  dev) directly — nginx/BFF should be the only path in.
- **`client_max_body_size` / proxy timeouts** at the nginx layer — currently absent from
  `deploy/nginx/nginx.conf`. Now that the app-side array-length cap (§4.1) rejects oversized
  *parsed* bodies quickly, a request-size cap at the proxy layer is still worth adding as a
  second line of defense against the raw bytes never reaching the app at all.
- **TLS termination** — confirm where it terminates; no plaintext hop should carry a JWT or
  the SSE ticket across an untrusted segment.
- **Puma worker/thread tuning** (`HANAMI_MAX_THREADS`, `HANAMI_WEB_CONCURRENCY`) — this pass
  sized the DB/Redis pools to track `HANAMI_MAX_THREADS` automatically (`config/database.yaml`,
  `config/providers/redis.rb`, both read `ENV['HANAMI_MAX_THREADS']` with a `+2` headroom for
  background-thread DB/Redis usage), so raising Puma's thread count now correctly raises both
  pools with it — no follow-up needed *there*, but the actual thread count itself is still an
  environment/ops decision, not made by this pass.
- **Load testing**: run realistic concurrency against `schedule_recommendations`,
  `schedule_events` writes, and both SSE endpoints (`/admin/stream` has a documented
  50-connection cap on `/admin/schedule/load/stream`) before calling the system load-tested.
  Now is a reasonable time to do this, since the DoS lever that would have made results
  meaningless (§4.1) is closed.
- **Backup/DR**: Postgres backup/restore drill, MinIO bucket replication/versioning — not
  assessed in either source doc, needs its own pass.
- **Observability**: wire the new `auth_failure`/`permission_denied` structured log events
  (§5/6, this pass) into actual alerting — they exist now but nothing is watching them yet.
  Also: request latency/error rate per endpoint, DB pool utilization, Redis latency metrics.
- **Secrets**: confirm production pulls secrets from a proper secrets manager, not an
  env-file pattern carried over from `.env.local`.

## 5. §3.6 — ClamAV signature refresh (infra, deferred)

No `freshclam` call exists anywhere in the Dockerfile/compose/entrypoints — signatures are
frozen at image-build time. Needs a scheduled `freshclam` run (cron sidecar, or a defined
rebuild cadence) before this is a real malware control rather than a point-in-time snapshot.
Concretely: either (a) add a `freshclam`-running sidecar container to `docker-compose.yml`
sharing the ClamAV signature volume with the scanning process, or (b) commit to a documented
minimum image-rebuild cadence (e.g. weekly) and track it operationally. (a) is more robust;
(b) is zero-code and may be acceptable depending on how often this environment rebuilds anyway.

## 6. Excel ingestion durable retry / dead-letter path (partially addressed)

The immediate OOM vector (§3.5 — decompressed zip-bomb size) is closed: `storage.py` now
rejects oversized archives before pandas ever touches them. What's still true: ingestion is
fire-and-forget over Redis pub/sub with no durable queue, so any *other* kind of processing
failure (a malformed-but-not-oversized file, a transient DB error mid-sync, a worker crash)
still drops silently instead of retrying or landing in a dead-letter queue. If ingestion
reliability becomes a real operational pain point, this is the next thing to revisit —
likely means introducing a proper job queue (Sidekiq/etc. or a Redis Streams consumer group
with acknowledgment) in front of `excel_processor`, which is a meaningfully larger change
than anything else in this list.

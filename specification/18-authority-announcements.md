# 18 — Authority, Announcements, and Priority Admission

**Scoped authority certificates, public announcement bundles, and Sybil-resistant priority admission for infrastructure-assisted deployments.** Status: extension-phase (rev. B) **FINAL**, 2026-07-03 (drafted 2026-07-02; council Round-2 fixes CR2-2/CR2-3/CR2-4 and Round 2-bis fixes CR2bis-2/10 (issuer revocation list, field 0x08, sticky union), CR2bis-3/11 (declared-priority wire ordering + §5.2.2 queue-jump residual), CR2bis-5/6 (self-contained AuthCert TLV 0x81) applied. The Round 2-bis panel is complete — both seats (Fable, then Sonnet post-limit-reset) reviewed independently and their blocking findings are fixed; ROADMAP Stage 9 still gates on a human-expert external review of the authority model before implementation). Citations [J*] in research/bibliography.md. Constants ⚠ provisional.

> Adds: authority certificates (AuthCert) binding a subject key to a scope with a rate-limited priority budget; a new public announcement bundle class; a scope registry reused as `dest`; and receive-side priority clamping gated on authority proof. Minimal wire footprint — all extension-safe per doc 03 §8 / doc 10 §3.1: **1 new bundle class (5), 2 new claim fields (0x07 AuthCert — see §2.1 correction; 0x08 REVOCATION_LIST — §6/CR2bis-10), 2 new signing-domain tags (`mmp1/authcert`, `mmp1/announce`), 2 new optional-range TLVs (0x81 AUTHCERT_ATTACH — §5.2.1/CR2bis-5; 0x82 SCOPE_INFO)**. No new frame type, no new RBSR domain, no new HELLO capability bit.

---

## 1. Threat model and goals

Cell-broadcast systems are the closest deployed analog to "one sender, many strangers, no session." They are also a documented failure case: LTE Wireless Emergency Alerts have **no device-side cryptographic verification** — an SDR fake eNodeB delivered a spoofed Presidential Alert to ~90% of phones in a 50,000-seat stadium simulation [J1], and the underlying 3GPP PWS design is unauthenticated *by design*, not by oversight [J4]. Hawaii's 2018 false missile alert shows the complementary failure: even with working crypto, a process without dual control turns one operator error into a mass event [J2]. A follow-up 5G PWS spoofing testbed confirms cross-cell verification schemes proposed since then do not generalize to disconnected/DTN settings [J3]. **The lesson MMP takes: never trade authenticity for availability.** Every AuthCert and every announcement is locally, cryptographically verified before it influences priority or display — WEA's model (accept and render unconditionally) is the one thing this doc must not become.

Goals, in order: (1) let a scoped authority (a railway operator, a campus org) publish public announcements that a client can render as *official* only when cryptographically warranted; (2) bound the abuse blast radius of a compromised or malicious authority key by construction, not by hope; (3) degrade honestly to "no authority" (Profile B) without inventing trust that doesn't exist; (4) do all of this without a global PKI, online CRL, or synchronized clock — the DTN constraints of docs 03/06 hold unchanged.

Two deployment profiles (doc 17 defines both fully; summarized here): **Profile A** (infrastructure-assisted) — an operator root key signs conductor/staff AuthCerts, pinned via QR at boarding with claim-gossip as fallback. **Profile B** (pure ad-hoc) — no authority exists; announcements from unverified senders MUST show an explicit "unverified" banner and MUST NOT render as official, ever.

**Disclosure (CR2-4): the operator root is this suite's first deliberate trust anchor.** Everything in docs 01–15 derives trust from TOFU + web-of-trust over self-minted keys — "no registration authority" (doc 03 §3.1) is a design axiom there. An AuthCert issuer is a scoped, opt-in departure from that axiom: within its one scope namespace it is, functionally, a small CA. This doc takes the position that the departure is honest and contained (scoped, expiring, budget-bounded, pin-or-gossip visible to the user) rather than pretending the anchor isn't one — and Profile B exists precisely so the protocol never *requires* it. §7 row A6 records what its compromise costs.

## 2. Authority certificates

```
AuthCert {
  subject         key32   // conductor/staff identity being granted authority
  scope           id16    // scope_id (§4) this cert is valid for
  caps            u8      // bit0 ANNOUNCE, bit1 PRIORITY_EMERGENCY (may use prio 0);
                          // absent bit1 caps the subject at prio 1 (OPERATIONAL). bits 2-7 reserved.
  priority_budget u16     // elevated-priority admissions per hour ⚠ (§5.2)
  not_after       u32     // wall-clock expiry, receiver's local clock (§6.3, CR-A6)
  issuer          key32   // operator root (or delegate) that signed this grant
  sig64                   // issuer's signature, mmp1/authcert scheme
}
```

Signed preimage (normative, CR-S4): `"mmp1/authcert"‖0x01 ‖ suite:u8 ‖ subject ‖ scope ‖ caps ‖ priority_budget ‖ not_after ‖ issuer`. The suite selector is included even though every field here is fixed-width, for the same cipher-agility reason doc 08 §9 reserves a suite byte in every handshake/claim — a future suite-0x02 AuthCert must not be confusable with a suite-0x01 one under a shared domain tag.

### 2.1 Claim field allocation — correction against the working assumption

The brief for this doc assumed claim field `0x06` was free (0x04 prekey, 0x05 friendship already taken). **That assumption is wrong**: doc 06 §4.1 already allocates `0x06` to `group_epoch_anchor`. AuthCert therefore uses **claim field `0x07`** instead — the next actually-free value, no other change to the design. `Claim{owner=subject, field=0x07, seq, body=AuthCert bytes, sig}`, signed by the *subject* under the ordinary `mmp1/claim` scheme (doc 06 §4.1) — the subject is asserting "I hold this grant," while the AuthCert body carries the issuer's independent `mmp1/authcert` signature proving the grant itself. This nested-signature shape has direct precedent: doc 06 §4.1 field 0x05 (friendship) already embeds a second, differently-scoped signature inside a claim body.

**Unknown-claim-field handling — now normative in doc 06 §4.1.** Doc 06 §4.1 states the rule directly: a claim with an unrecognized `field` is stored and re-offered (the claim wrapper's own `mmp1/claim` signature is independently checkable) but its body is opaque and never interpreted — the same posture as unknown bundle classes (doc 03 §8) and unknown optional TLVs (doc 03 §4.4). **Fallback, still useful for latency reasons even though the rule is now confirmed:** carry the AuthCert instead as optional-range TLV `0x81 AUTHCERT_ATTACH` on the announcement bundle itself (RECOMMENDED for all elevated-priority announcements — §5.2.1), which is unambiguously ignore-if-unknown per doc 03 §4.4. The primary design below uses claim field 0x07 gossip for cross-session propagation; the TLV-0x81 fallback remains the faster path for self-contained announcement bundles either way (§5.2.1's latency argument, independent of the confirmation above).

**Singleton-slot limitation (noted per CR2bis-10's class of bug):** `(owner=subject, field=0x07)` is one LWW register, so claim gossip carries only a subject's *most recent* grant. A subject holding multiple concurrent AuthCerts (e.g., two scopes) cannot gossip them all; it relies on TLV `0x81 AUTHCERT_ATTACH` (§5.2.1) to carry the applicable cert with each elevated announcement — which is the RECOMMENDED path regardless. Single-grant subjects (the Profile A norm: one conductor, one scope, one shift) are unaffected.

### 2.2 Trust root and provisioning (OQ-16)

Two trust levels for an operator root key: **pinned** (scanned from a physical QR at boarding — strong, out-of-band) and **gossiped** (learned as an ordinary claim from other nodes — weak, TOFU-consistency only, subject to the same first-contact MITM limits as any TOFU trust in doc 07 §6.1/matrix #2). Apps MUST render these two states distinguishably (doc 07 §6.1 precedent). QR-scan friction, poster-replacement spoofing, and gossip-consistency detection quality are unvalidated — OQ-16 tracks this, resolved via the doc 18 persona review (§10) now and a field pilot later.

## 3. Announcement bundles

**Decision: new bundle class 5**, not a message addressed to a scope-as-GroupID under class 2.

| Option | Mechanism reused | Verdict |
|---|---|---|
| Class 5 (chosen) | New bundle class, values 5–15 free (doc 03 §4.1); extension-safe: legacy nodes store-and-forward blindly if signature verifies and TLVs are non-critical, never process (doc 03 §8) | **Chosen** — clean separation from group semantics; plaintext by design (announcements are public); no OR-Set/epoch machinery needed |
| Class 2 to a scope-as-GroupID | Reuses group message class, treating the scope as a pseudo-group | **Rejected** — overloads group machinery (sender-keys epochs, OR-Set membership, admin model, doc 06 §8) that has no meaning for a public, unencrypted, non-membership broadcast; would force every announcement through group re-keying semantics it doesn't need |

Announcement bundle: `class=5`, `dest = scope_id` (§4, reusing the frozen `dest` field verbatim — zero wire change), `priority` = the named class the origin declares (§5.1), payload = **plaintext** (never AEAD — announcements are public by nature, and plaintext lets any node, verified or not, render/relay without key material). Payload schema:

```
AnnouncementBody {
  ann_type   u8         // 0 delay, 1 platform_change, 2 safety_emergency, 3.. reserved
  scope      id16       // redundant with dest, explicit for payload-level display/audit
  not_after  u32        // announcement's own display-validity, wall clock (may be shorter than lifetime_ms)
  text       varbytes   // UTF-8, length-delimited (doc 10 §1 varbytes primitive)
  sig64                 // inner signature, mmp1/announce scheme, by the authority SUBJECT key
}
```

Signed preimage (CR-S4): `"mmp1/announce"‖0x01 ‖ suite:u8 ‖ scope ‖ ann_type ‖ not_after ‖ len(text):u16 ‖ text`. **Why an inner signature when the bundle itself is already Ed25519-signed by `origin` (= the subject) over the whole canonical payload (doc 03 §4.1)?** Because the bundle store is TTL-bounded and evicts (doc 03 §4.3), while an app's *notification/announcement history* reasonably outlives the bundle — the inner signature lets a cached announcement be re-verified standalone after the wrapping bundle is gone, without re-deriving bundle-canonicalization rules for an object that by then no longer exists. Defense-in-depth at negligible cost (one more Ed25519 verify, already budgeted per doc 13).

Scope metadata rides in a new **optional-range TLV `0x82` SCOPE_INFO** on the bundle (doc 03 §4.4: 0x80–0xFF ignore-if-unknown): `(scope_name_hint varbytes)` — a human-readable scope label for UIs that haven't resolved `scope_id` back to a name yet (§4). Being optional-range, a legacy node that doesn't understand TLV 0x82 simply ignores it and still relays the bundle if the outer signature verifies — no interop hazard.

**No new frame type, no new HELLO negotiation.** Class-5 announcements travel inside the existing `0x20 BUNDLE` frame (doc 10 §2) unchanged — only the bundle's own `class` nibble is new. A rev-A node's frame parser needs zero awareness of class 5 to relay it correctly.

## 4. Scope registry

`scope_id = BLAKE3("mmp1/scope" ‖ scope_name)[0..16]` — a deterministic, collision-resistant 16-byte identifier from a human-readable name, requiring no registrar (same self-certifying-namespace posture as identity, doc 03 §3.1). Well-known scope name grammars: `train/<operator>/<service>` (e.g. `train/nationalrail/1234`), `campus/<org>`. `dest = scope_id` reuses the frozen bundle `dest` field — doc 03 §4.1 already types `dest` as "NodeID, GroupID, **or well-known scope ID**," so this is a zero-wire-change reuse, not an extension.

**Subscription is a local filter, not a protocol object.** A node holds a set of `scope_id`s it cares about (configured from scope *names* it resolves locally) and uses that set only to (a) decide whether to render an announcement prominently and (b) weight D3 relay-spray admission for class-5 bundles matching a subscribed scope (doc 05 admission, unchanged mechanism). No subscription state is ever transmitted — a stranger scanning beacons or sessions learns nothing about which scopes a node subscribes to.

**Reconciliation-domain constraint (explicit).** A cleaner design would give class-5 announcements their own RBSR domain (doc 06 §2's D0–D4), but a **new DOMAIN value requires a new HELLO capability bit** (doc 10 §2.1 `flags`) to negotiate safely with legacy peers — exactly the kind of wire change this doc is scoped to avoid. **Announcements therefore reconcile inside the existing D3 domain** (general relay-spray inventory, doc 06 §2) alongside every other non-D0/D1/D2 bundle. Cost: announcements compete for D3 airtime/quota like any spray traffic rather than getting a dedicated fast lane; benefit: zero negotiation surface, works against every rev-A peer on day one.

## 5. Priority admission

### 5.1 Named priority classes

The bundle header's existing `priority: u8` field (doc 03 §4.1, values 0–3, no wire change) gets named semantics for class-5 bundles:

| Value | Name | Meaning |
|---|---|---|
| 0 | EMERGENCY | Safety-critical (evacuation, incident) |
| 1 | OPERATIONAL | Service-affecting (delay, platform change) |
| 2 | NORMAL | Default / unauthenticated ceiling |
| 3 | BULK | Non-urgent (⚠ reserved, unused v1) |

### 5.2 Authority-gated admission (CR-A1: the answer to Sybil-defeated origin buckets)

**A bare priority byte with per-origin token buckets cannot bound priority abuse — because origin identity is free.** This is not a hypothetical: the council's Sybil finding (CR-A1) showed that any admission scheme metered purely by *origin key* is defeated by minting fresh keys, since nothing about a fresh key is more expensive to an attacker than an old one (doc 07 matrix #4, same base-rate-times-N_keys arithmetic applies here). Named priorities 0–1 are therefore honored — in **receiver-local admission and rendering** (what a node stores prominently, notifies on, and displays as official; wire-phase ordering is a separate matter, §5.2.2) — **only when the bundle's `origin` matches an AuthCert.subject for a scope the receiver subscribes to, that AuthCert verifies, is unexpired per the receiver's clock (§6.3), and its per-authority token bucket (§5.3) has remaining budget.** Otherwise the bundle's declared priority is **clamped to 2 (NORMAL) on receive** — this is the third instance of the established doc 03 clamp idiom (lifetime, §4.3; copy-budget, §4.5; priority, here).

**Reconciliation-set partitioning uses the DECLARED priority, never the clamped one (normative, CR2bis-3).** Doc 03 §5.2 phase 3 partitions RBSR BundleID sets *per priority class*. Bucket state and AuthCert visibility are per-receiver by construction (each node's admission history and claim-gossip state differ), so two honest peers can compute **different effective priorities for the same bundle** — if effective priority fed the RBSR partition, they would place the same BundleID in different sets and generate systematic spurious fingerprint mismatches in D3. RBSR partitioning therefore MUST key on the wire-visible, signed `priority` byte, which is identical at both peers; the clamp governs only receiver-local admission (store/queue policy) and rendering-as-official — **not wire-phase ordering, which follows the declared byte throughout v1 (§5.2.2)**.

**This clamp is a local scheduling interpretation, not a wire mutation — a real asymmetry against the other two clamps.** `lifetime_ms` and copy-budget are the *only* fields doc 03 §4.5 carves out as legitimately relay-mutable; `priority` sits inside the signed canonical bytes (doc 03 §4.1) and is never rewritten (doing so would break the bundle signature). "Clamp to 2" means: each honest node, applying the same *rule* to its own local facts (declared priority, its AuthCert view, its bucket state), computes an effective priority for its own admission and rendering decisions — deterministic per node, without any node persisting a changed byte on the wire. Stated honestly (CR2bis-3): those local facts *differ across nodes* (buckets are never shared state, claim gossip is asynchronous), so effective priority is per-receiver, not a network-wide agreement — which is exactly why the RBSR partition above must use the declared byte. A corollary: because the decision is made once per node at (re-)evaluation time rather than carried as protocol state, a receiver that admitted a bundle at NORMAL before a late-arriving AuthCert claim converges does not retroactively re-*admit* it against the bucket — the one-shot character of the lifetime/budget clamps — though it MAY re-evaluate *rendering-as-official* once the cert verifies (§5.2.1).

### 5.2.2 What the clamp does NOT govern: wire-phase ordering (honest residual, CR2bis-11)

Doc 03 §5.2 phase 3 processes RBSR partitions "highest priority first," and doc 05 §6 sorts spray TRANSFER by "priority class asc" — both keyed on the **declared** byte, both frozen, and neither has (or, per CR2bis-3, *could* soundly have) any admission concept. Consequence, stated plainly rather than papered over: **any origin can self-declare priority 0/1 on junk and receive earlier-in-session RECONCILE and TRANSFER service for it, with no AuthCert anywhere in that path.** The clamp cannot close this — it is receiver-local and per-receiver-divergent, exactly the properties that disqualified it from feeding reconciliation (CR2bis-3); an earlier draft of this section claimed the clamp governs "TRANSFER ordering," which doc 05 §6's actual rule does not support, and that claim is withdrawn. What bounds the abuse instead: priority buys *order, never volume* — per-origin token buckets (doc 05 §8) and store quotas are priority-blind, SeenIndex dedup (doc 03 §4.2) caps re-service, and the 60 s session cap (doc 11 §7) bounds how much "earlier" is worth per contact; the attacker gets its junk serviced sooner within budgets it cannot enlarge — a scheduling nuisance of the CR-A1 class, not an amplification. §7 row A7 records it; the structural fix (an admission-aware sort key in doc 05 §6) belongs to the frozen suite and is filed as an errata-candidate in `CHANGELOG.md`.

### 5.2.1 Self-contained elevated announcements (RECOMMENDED, CR2bis-5)

In the target deployment the audience is mostly strangers to the announcer, and AuthCert claims travel interest-scoped claim gossip (doc 06 §4.3) — so for a large fraction of receivers the cert would otherwise arrive *after* the announcement, and the one-shot clamp (§5.2) would leave a genuine EMERGENCY rendered and queued as NORMAL precisely when it matters. Two mitigations, both compatible with legacy relays:

1. **Carry the cert with the bundle.** Class-5 bundles declaring priority 0 or 1 SHOULD attach their AuthCert in optional-range TLV **`0x81 AUTHCERT_ATTACH`** (ignore-if-unknown per doc 03 §4.4 — a rev-A relay forwards it blindly). A receiver evaluating §5.2 admission MUST accept a verifying attached cert exactly as it would a gossiped one (same verification, same bucket). This makes elevated announcements self-contained at the cost of one AuthCert (~150 B) per bundle — negligible against MAX_BUNDLE. This is the same TLV slot §2.1 reserves as the unknown-claim-field fallback; the two uses are identical in format and never conflict (one cert, one meaning).
2. **Rendering may catch up; admission does not.** A receiver that clamped a bundle before the cert was known MAY re-evaluate the *rendering* decision ("official" banner, notification prominence) when the cert later verifies — rendering is a pure function of (announcement, cert) with no anti-abuse state. The *bucket* decision is never retroactively re-run (§5.2 corollary): re-admission bookkeeping after the fact would make the §5.4(c) accounting path-dependent for no abuse-resistance gain.

### 5.3 Per-authority token bucket

Each receiver meters elevated-priority admissions **per AuthCert.subject**, independent of relay path: bucket capacity and steady-state refill rate = `priority_budget` (§2, admissions/hour ⚠), decremented on each *distinct* class-5 BundleID admitted at declared priority (duplicates are already suppressed by SeenIndex + per-class dedup, doc 03 §4.2, before they'd reach the bucket). This directly bounds blast radius: **abuse radius ≤ budget × remaining_validity, by construction** — see the formal lemma below.

### 5.4 N3 — honesty and formal bound

**(a) Prior art this design is *not*.** Cryptographic mechanisms exist that enforce a rate budget *before* an action can even be produced, not merely account for it afterward — k-times anonymous authentication (Teranishi et al., 2004) [J15] lets a token holder authenticate at most k times per epoch, unforgeable and unlinkable, and offline e-cash double-spend detection (Chaum et al.) [J16] cryptographically identifies a double-spender from two uses of the same coin, without a live server at spend time. Both prove that offline, cryptographically-enforced budget primitives are a known, implementable category. **MMP's design does not adopt either.**

**(b) What MMP actually does — accounting, not prevention, stated plainly.** The §5.3 token bucket is enforced *by each honest receiver, locally, on receipt*. It contains no cryptographic mechanism that makes exceeding the budget *unforgeable* the way Teranishi-style k-times auth does — a colluding set of receivers can simply choose not to decrement their buckets, or not to check them at all, and admit unlimited priority-elevated bundles from a compromised AuthCert. **This is not a gap being hidden: honest-receiver accounting is exactly what a DTN with no online arbiter and no synchronized clock can offer** (the same structural limit doc 08 §6.5 and doc 06 §8.6 already document for group removal latency). Adopting a cryptographic k-times-style primitive here is future work (doc 15 R19/R20) — not v1 scope, and not silently implied.

**(c) Formal lemma (the citable claim).**

> *Lemma (tightened per CR2-3).* A single AuthCert `C` with `priority_budget = β` (admissions/hour), bucket capacity `B ≤ β` (§5.3), and remaining validity `T = C.not_after − now` hours (receiver's local clock) causes at most **`B + β·T ≤ β·(T+1)`** distinct class-5 bundles to be admitted at declared priority (0 or 1) by any single honest receiver, regardless of how many relay copies deliver it.

> *Proof.* (1) A receiver `R` admits a class-5 bundle at declared priority only if: `origin = C.subject`, `C` verifies under `mmp1/authcert` for a scope `R` subscribes to, `C.not_after` has not passed `R`'s local clock (±skew, §6.3), and `R`'s local bucket for `C.subject` has ≥1 token (§5.3). (2) `R`'s bucket is local state, decremented once per *distinct* BundleID — SeenIndex and per-class dedup (doc 03 §4.2) guarantee re-delivery of the same bundle via additional relay paths never re-decrements it. (3) Tokens available over `[now, C.not_after]` = tokens present at `now` (≤ capacity `B`) plus tokens refilled during the interval (≤ `β·T` by the rate integral); with `B ≤ β` this totals ≤ `β·(T+1)` — the initially-full-bucket term is *bounded explicitly*, not absorbed. (4) Every admission the receiver honors consumes one of those tokens, and steps (1)–(3) hold independently at every receiver — no shared bucket state exists across nodes — so the bound is per-receiver-partition, not global-additive over relay fan-out. ∎
>
> *Boundary conditions, stated rather than implied:* the bound is **per certificate** — issuer renewal mints a fresh budget by design (that is what renewal means), so the *issuer* is the true root of the bound (see §7 row A6 for issuer compromise); and `T` is measured on each receiver's own clock, so a receiver with a badly-wrong clock over-admits only locally (CR-A6 damage containment, §6.3).

This is the result the council's N3 disposition (`COUNCIL-REVIEW.md`, Round 1) asked for: a short, receiver-local, DTN-honest bound that survives arbitrary relay-count amplification, in contrast to unbounded schemes like BPv7 priority classes, which carry **no sender authentication and no abuse resistance at all** [J8].

## 6. Revocation

**Expiry-first (primary).** `not_after` (§2) is deliberately short-lived — sized to a shift length (⚠, doc 17 train contact model), so a compromised AuthCert self-limits without any active revocation step. **This ordering is not stylistic: both explicit-revocation paths below have adversarial limits, so expiry is the only defense that works unconditionally.**

**Explicit revocation (backstop, corrected per CR2bis-2).** Two distinct paths, with honestly different power:

- **Subject-signed tombstone** — the subject publishes a fresh claim at its own `(owner=subject, field=0x07)` slot with a bumped `seq` and an empty body; ordinary claim-LWW (doc 06 §4.2). **Limit, stated plainly:** this path works for *retirement and device loss*, not for *key theft* — an attacker holding the subject key holds the same LWW pen and can out-`seq` any tombstone indefinitely. LWW is symmetric between the two holders of one key; a subject-signed tombstone must never be presented as a defense against A1.
- **Issuer-signed revocation list (the theft-capable path; slot design corrected per CR2bis-10).** The issuer cannot write into the subject's claim slot (claims are owner-signed, doc 06 §4.1), and — the second seat's catch — it also cannot publish *per-subject* revocations as separate values under one of its own `(owner, field)` slots, because doc 06 §4 makes each such slot a **singleton LWW register**: a later revocation for subject B would supersede subject A's in claim-digest sync (doc 06 §4.3 ships only the current value per key), silently un-gossiping A's revocation. The issuer therefore publishes its **entire current revocation state as one value**: claim field **`0x08 REVOCATION_LIST`** under `(owner=issuer, field=0x08)`, body = `suite:u8 ‖ count:u8 ‖ count × RevEntry{subject key32, scope id16, not_after u32}`, authenticated by the ordinary `mmp1/claim` owner signature (the issuer *is* the authority for its own revocations; receivers additionally check `owner` equals the issuer they trust for the scope). Rules (normative): each update carries **all** revocations whose `not_after` has not yet passed (expired entries MUST be pruned by the issuer — shift-length certs keep the list naturally small); `count ≤ REVLIST_MAX = 48` ⚠ (≈2.5 KiB body, safely under MAX_BUNDLE with claim overhead; an issuer that overflows this cap is churning subjects faster than revocation gossip can serve and should rotate the root instead — the §7 A6 floor). **Receiver rule ("revoked wins, sticky"):** a receiver maintains the *union* of every verified RevEntry it has ever seen from that issuer, each honored until its own `not_after` — so elevated admission for a revoked `(subject, scope)` stays refused even if a later (mistaken or malicious-issuer) list omits the entry. This is a deliberate, narrowly-scoped departure from LWW symmetry — deliberate because LWW symmetry is precisely what the thief exploits in the subject-signed path; scoped because it applies only to admission triples `(subject, scope, issuer)`, never to general claim merge (the *claim* still merges LWW; only the receiver's admission memory is sticky). The thief cannot forge into the issuer's slot and cannot un-see an entry at receivers that hold it; residuals: receivers the list has not yet reached (gossip-speed propagation, OQ-17) still admit within §5.4(c)'s bound, and field `0x08` inherits §2.1's unknown-claim-field assumption exactly as `0x07` does.

**Why not an online CRL (CR-A6, no shared clock).** A DTN has no trustworthy shared clock and no reachable revocation server by definition (doc 03 §1 network model) — the online-CRL pattern (and TESLA-style delayed-key-disclosure broadcast auth, which needs *bounded receiver clock sync* [J5], structurally incompatible with multi-hop DTN propagation delay) is not adaptable here, and a TESLA-for-5G-style adaptation still targets live cellular reachability, not delay-tolerant mesh [J6]. `not_after` is therefore enforced against the **receiver's own local clock**, with a stated skew tolerance of 15 min ⚠ (matching the coarse_time_slot tolerance style of doc 03 §5.1.1); when clocks disagree beyond that, the tombstone claim (above) is the backstop, propagating at ordinary DTN claim-gossip speed (OQ-17 models this against typical shift-length cert lifetimes — best guess: shift-length certs make explicit revocation a second-order defense behind expiry). Reference: doc 15 R19 (no-shared-clock expiry enforcement pattern).

**Scoped instance of a general problem (CR-A7).** AuthCert revocation-over-DTN is not a new primitive — it is a **scoped instance of the general self-certifying-key-revocation-over-DTN problem** that applies to identity keys, group admin keys, and exchange keys alike (doc 15 R20). It reuses claim-LWW tombstoning precisely because that mechanism is already general-purpose. For comparison, the closest deployed no-CRL pattern is V2X's ACPC scheme, which withholds periodically-broadcast activation codes from revoked vehicles [J9] — but ACPC assumes periodic infrastructure connectivity that a partitioned mesh cannot guarantee, so MMP falls back to gossip-speed tombstones rather than activation-code withholding. Delegation-token systems with offline verification (macaroons [J10], Biscuit [J11], UCAN [J12], Vouchsafe [J13]) all support offline *attenuation*, but none carries a native rate-budget primitive — confirming §5.4(a)'s point that the token-bucket accounting here is a genuine (if modest) addition, not a reuse of an existing offline-delegation budget mechanism.

## 7. Abuse analysis

| # | Attack | Vector | Defense | Residual risk |
|---|---|---|---|---|
| A1 | Stolen conductor key | Attacker exfiltrates a live AuthCert's private key | §5.4(c) lemma bounds elevated-priority injection to `budget × remaining_validity`; expiry-first (§6) shrinks the window; the **issuer revocation list** (§6, field 0x08, sticky union) revokes once detected — the *subject-signed* tombstone is useless here, since the thief holds the same key and out-`seq`s it (CR2bis-2/10) | Bundles admitted before the revocation list propagates are genuinely authority-signed and cannot be un-admitted after local render (accounting, not prevention — §5.4(b)); bounded, not zero |
| A2 | Replay of a valid announcement | Re-inject a captured, still-valid announcement bundle | SeenIndex-from-first-sight + lifetime clamp (doc 03 §4.2/§4.3), unchanged; per-bundle-ID dedup at the token bucket (§5.4 step 2) | One quota-bounded relay store/offer cycle past the dedup horizon, same residual as doc 07 matrix #17 |
| A3 | Cross-scope priority injection | Attacker holds a valid AuthCert for scope X, tries to elevate priority for scope Y traffic | Admission requires `C.scope` match the receiver-subscribed scope of *this* bundle's `dest` (§5.2) — a cert for X grants nothing for Y | None beyond the same-scope blast radius already bounded |
| A4 | Profile-B Sybil authorities | No operator root exists; attacker self-issues AuthCert-shaped claims | Profile B has no trust root to pin or gossip against — the client simply never has a `mmp1/authcert` chain rooted anywhere trusted, so priority 0/1 never admits; UI shows the "unverified" banner for *every* sender, self-authority included | Depends entirely on the UX banner being non-bypassable; a client bug that renders unverified content as official defeats the whole doc — flagged for doc 12 conformance tests |
| A5 | False-panic announcement (authority key intact, sender malicious or mistaken) | A legitimately-authorized conductor issues a false EMERGENCY announcement | Out of cryptographic scope by design — same class of failure as Hawaii 2018 [J2], which was a *process* failure, not a crypto one; mitigation is accountability (the announcement is non-repudiably signed, doc 08 §11.1 precedent) plus UX: EMERGENCY-class announcements SHOULD surface the signing subject's identity, not just "official," so accountability is visible | Social/procedural, not protocol-solvable; documented rather than hidden, per doc 07 §7 house style |
| A6 | **Stolen operator ROOT key (issuer compromise — the worst case, CR2-2)** | Attacker exfiltrates the operator root private key and mints unlimited fresh AuthCerts (arbitrary subjects, max caps, max budgets); §5.4(c)'s per-cert bound does not help because the attacker renews at will | Cert-level defenses are structurally void here — the only real containments are: (1) the root is only as reachable as its pinning ceremony (a pinned-QR root compromised at the printer is a *provisioning* attack, OQ-16); (2) issuance SHOULD be dual-controlled at the operator (the [J2] Hawaii lesson applied to minting, not sending); (3) recovery = publishing a new root + physically re-pinning (new QR posters) — gossip alone cannot outrun an attacker who also gossips, so re-pin is the floor; (4) scope containment: the stolen root grants nothing outside its `scope` namespace — campus roots don't fall with train roots | **Unbounded within the scope until re-pin** — stated plainly. This is the standard, irreducible PKI-root risk, scoped to one operator's namespace rather than a global CA; the design's honest answer is a small blast *surface* (one scope), not a small blast *radius* |
| A7 | Declared-priority queue-jump (no authority needed, CR2bis-11) | Any origin self-declares priority 0/1 on junk bundles (class 5 or otherwise); frozen wire-phase ordering (RECONCILE partition order, doc 03 §5.2 phase 3; TRANSFER sort, doc 05 §6) services them earlier in every session | None at wire-phase ordering in v1 — stated plainly (§5.2.2). Bounds: priority buys order, never volume — per-origin token buckets and store quotas are priority-blind; SeenIndex dedup caps re-service; 60 s session cap bounds the per-contact gain | Earlier-in-session service for junk within unenlarged budgets — CR-A1-class scheduling nuisance; structural fix (admission-aware sort key in doc 05 §6) filed as errata-candidate |

## 8. Legacy interop

A rev-A node with no knowledge of class 5, claim fields 0x07/0x08, TLVs 0x81/0x82, or the two new signing-domain tags relays every announcement bundle **correctly and blindly**: it verifies the outer `mmp1/bundle` signature (unaffected — domain separation means the new tags never collide with what it checks), sees an unrecognized `class` nibble, and store-and-forwards per doc 03 §8's existing rule (unknown classes relay if signature verifies and TLVs are non-critical; TLV 0x82 is optional-range so it always qualifies). It never renders, never applies priority admission (§5.2, since it doesn't parse `AnnouncementBody`), and never risks misinterpreting a claim field 0x07 body it doesn't understand (§2.1's assumption). **Relay cost:** identical to any other class-5-sized bundle in D3 spray accounting (§4) — no legacy-node penalty beyond ordinary quota consumption; a rev-A fleet is a strictly-passive carrier for announcements until upgraded.

## 10. Persona review checkpoints

- **Security Auditor — Potential flaw:** "The receive-side priority clamp (§5.2) is enforced by receivers who can simply choose not to enforce it — a colluding set of receivers admits unlimited elevated traffic." *Resolution:* correct, and stated as a first-class limitation, not discovered late — §5.4(b) says this explicitly. The lemma (§5.4c) bounds what *honest* receivers admit; it is accounting, never cryptographic prevention. No DTN-appropriate primitive currently closes this gap (§5.4a); flagged for future work, not silently assumed away.
- **Skeptical Professor — Potential flaw:** "Claim field 0x06 collides with `group_epoch_anchor` (doc 06 §4.1) — the brief got this wrong." *Resolution:* caught and corrected in §2.1; field 0x07 used instead, with a TLV-0x81 fallback documented in case the deeper unknown-claim-field assumption also fails. This is exactly the kind of cross-doc collision test vectors and careful re-reads exist to catch (doc 10 §8 precedent).
- **Performance Engineer:** the inner `mmp1/announce` signature (§3) is a second Ed25519 verify per announcement, on top of the bundle-level one. *Resolution:* announcements are low-frequency relative to direct/group messages (doc 13 traffic model); the second verify is justified by outlasting bundle-store TTL (§3) and is a rounding error against the SUMMARY-phase cost already dominating contact budgets (doc 10 §7).
- **Distributed Systems Reviewer:** reusing D3 for announcement reconciliation (§4) means announcements compete with ordinary spray traffic for airtime rather than getting a fast lane, even for EMERGENCY-priority ones. *Resolution:* accepted tradeoff — a dedicated domain needs a HELLO capability bit, which is exactly the wire-change surface this doc is scoped to avoid; EMERGENCY urgency is served by *declared*-priority-ordered RECONCILE/TRANSFER (doc 03 §5.2 phases 3–4, doc 05 §6) within D3, not by a separate domain — which cuts both ways: the same declared-byte ordering serves self-declared junk equally well (the §5.2.2/A7 queue-jump residual, CR2bis-11). Revisit if field data shows this insufficient.
- **Battery Specialist:** the per-authority token bucket (§5.3) adds one more piece of persistent per-subject state on Core (`no_std`) receivers. *Resolution:* bounded by the number of distinct AuthCert subjects a node has ever admitted from — realistically single-digit per deployment (one operator's conductor roster); negligible against doc 08 §12's skipped-key-window budgets on the same tier.
- **Inventive Scientist — tasked with N3:** "Is the token-bucket-plus-clamp construction actually novel, or does it just relabel an existing primitive?" *Resolution (§5.4):* it is not claimed as a cryptographic novelty — §5.4(a) names two schemes (Teranishi et al. k-times auth; Chaum et al. offline e-cash) that *do* achieve cryptographic offline enforcement, and MMP explicitly does not adopt either. The citable contribution is narrower and honestly scoped: a receiver-local accounting bound with a proved per-partition ceiling (§5.4c lemma) for a DTN with no online arbiter — the delegation-token literature surveyed in §6 (macaroons/Biscuit/UCAN/Vouchsafe) offers offline attenuation but no rate-budget primitive at all, so even this modest bound is new *among offline delegation schemes specifically*, not among cryptography generally.

# Local scheduling prototype

This is the local CP-SAT worker for the [scheduler design](../../docs/architecture/scheduler-design-draft-2026-09-28.md). It accepts JSON snapshots and has no database access. Hanami builds and authorizes snapshots, stores private generation runs and proposals, and remains the only service allowed to publish timetable changes.

The preference compiler sends calendar-specific weekday requests (such as “the first Monday of the month”), multiweek intervals (such as “every other week”), and relative lesson-period windows (such as “only after the second pair”) to administrator review. Its typed rule schema currently represents weekly weekdays, lesson periods, and even/odd week parity, so these phrases must not be broadened into unconditional weekly rules.

The Python base image is pinned by digest in `Dockerfile`, and `requirements.txt` pins OR-Tools plus its complete installed dependency set. This keeps local rebuilds on the same solver and Python package versions instead of resolving newer transitive releases.

Create a Python virtual environment, install `requirements.txt`, and run:

```sh
python main.py ../../docs/architecture/scheduler-synthetic-scenario-2026-09-29.json --operation analyze
python main.py ../../docs/architecture/scheduler-synthetic-scenario-2026-09-29.json --operation compile-preferences
python main.py ../../docs/architecture/scheduler-synthetic-scenario-2026-09-29.json --operation generate
```

The analyzer reports teacher/group/room clashes, profile unavailability, room capacity and unassigned-room errors in the synthetic scenario. It also reports unmet approved soft wishes as non-blocking review findings; only error-severity findings prevent publication. Room capacity is optional and enforced when present; shared streams need room capacity for the sum of linked group sizes. Room software/equipment wishes are retained with an explicit review finding, but never become solver constraints until a trusted capability catalog exists. The conservative preference compiler proposes supported Russian wishes and sends unclear or unsupported ones to administrator review. Only entries in `approved_preferences` affect the CP-SAT objective. Existing split lessons can be reassigned between subgroups in a private proposal, but the analyzer requires paired edits to preserve each subgroup's credited hours. The solver respects published lessons and hard constraints, produces one placement per remaining weekly meeting, and returns a validated proposal.

The snapshot schema models project-derived remaining lesson units, teacher teams, group subgroups, compatible shared lecture streams, recurring parity, semester-wide published teacher/group/room blockers, profile availability, room assignments and reservations, and conservative occupancy blockers for dated and weekday transfers. Faculty scope limits which workload is generated, while resource occupancy remains semester-wide so proposals avoid teachers and rooms used by other faculties. Existing blocker rows retain only the identities needed for conflict checks; unsupported external week parity is conservatively treated as occupied in both weeks. Teachers can submit Russian text from the authenticated cabinet; the local compiler produces versioned typed proposals and review findings that are stored durably. It recognizes weekday inflections, numbered periods before or after the word “пара” (including lists and ranges), ordinal periods through the ninth pair, and explicit even/odd week scope. For grounded weekday/period wishes, explicit negations such as “предпочитаю не проводить занятия” and “нежелательна первая пара” compile as soft unavailability; double-negated, ambiguous and unsupported phrasing remains in administrator review rather than being broadened silently. Day lists joined as conjunctions become one rule per day; alternative day choices and contradictory week scopes remain in review. An unnamed wish for two consecutive lesson units is scoped to the teacher, even when they have multiple workload requirements. A uniquely named subject scopes the wish to that requirement; a named subject with zero or multiple exact matches, or no semester workload, remains in review. Only an exact count of two with a recognized lesson noun becomes the supported consecutive preference. Other counts, ranges, ordinal counts, vague quantities, qualifiers such as “at least,” and non-lesson units remain in administrator review; the solver scores adjacent lesson pairs and cannot guarantee longer chains. Oven/heating wording is treated as a reason and never inferred to name a laboratory subject. Only administrator-approved supported proposals enter a later generation snapshot. Explicit profile unavailability remains a hard constraint; profile availability and text-based available/unavailable wishes are soft scores. Text wishes that oppose hard profile unavailability are flagged for review and excluded from solver scoring. The compiler is grounded in the request's semester slot catalog: a numbered period absent from that catalog is a review finding, never an approved proposal; the catalog also participates in the context fingerprint so approvals cannot outlive a changed set of valid slots. Hanami exposes explicit row-selective publication with revision and source-digest checks, final analysis, existing event validation and transactional Outbox writes. Unselected rows remain in the private run and can be published later. Administrators can edit proposed weekday, period, eligible room and supported week parity; the API limits parity choices to those valid for the generated lesson unit. Protected heartbeats report preparation and search while no feasible solution exists, then validation; coalesced incumbent updates add solution count, placed units, branches, solver conflicts, elapsed time, objective and bound. Each run is private to its requesting administrator. Reads, edits, cancellation and publication require matching that requester account, including for super-administrators. The run owner sees progress in the existing polling view, including the final summary. Cancellation clears the private snapshot and progress capability and signals the active worker through its rejected heartbeat; it does not publish schedule changes. Callback authorization uses a per-run random capability whose SHA-256 digest is stored only for the active lease. Compatible shared lecture requirements with matching teacher assignments and lesson units, with only rooms eligible for every member are emitted as one solver placement and published through the existing linked-event batch operation. Incompatible stream data is rejected explicitly. Administrators can stage recurring lesson moves and dated occurrence corrections without writing the published timetable; recurring subgroup changes require balanced paired edits, while a dated subgroup override is stored on that transfer and used by the shared occurrence resolver.

## Internal service

`docker compose up --build scheduler` starts the pinned solver as an internal-only HTTP service. It has no database credentials or published host port. The API container can reach it at `http://scheduler:8100`; requests carry the same schema-versioned snapshot as the CLI:

* `GET /health`
* `POST /v1/solve` with optional positive-integer `X-Solve-Seconds`; without the header there is no fixed solver deadline
* `POST /v1/analyze`
* `POST /v1/compile-preferences`

Bodies are limited to 8 MiB, request logs omit snapshot contents, and only one CP-SAT solve runs at a time; concurrent solve requests receive `429 SOLVER_BUSY`. The API worker treats that response as capacity contention: it returns the run to the durable queue with capped exponential jittered backoff, tracks contention separately from solver-failure attempts, and does not consume the solver-failure budget. Other scheduler/network failures keep their bounded retry policy. Compose attaches the service only to an internal network and applies CPU/memory limits. Solve runs have no fixed deadline by default, while `SCHEDULER_SOLVE_SECONDS` can impose a positive operator-selected limit. The API worker refreshes its database lease independently from solver progress. If the worker dies, lease expiry transfers ownership; the old solver sees its invalidated progress capability and stops. Progress remains visible while search continues. The status endpoint returns the run owner a proposal without exposing the original snapshot. Publication still requires a separate validated, atomic API operation.
